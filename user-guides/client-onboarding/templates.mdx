**Audience:** MSP staff configuring and managing client onboarding. Company users should start with [Open your onboarding portal](/user-guides/client-onboarding/open-your-onboarding).

## Before you begin

Your organization must have Client Onboarding enabled. Viewing requires onboarding read access; creating or changing templates and portals requires onboarding write access and active billing. **Convert to Client** requires onboarding management access. Your role and company scope can limit what appears.

Templates are reusable blueprints that define your onboarding process. Each template contains phases (workflow stages) and tasks (individual action items) that get copied into a portal when you launch onboarding for a client.

## Creating a Template

<Steps>
  <Step title="Navigate to Templates">
    Go to **Settings > Onboarding > Templates** and click **New Template**.
  </Step>
  <Step title="Set Template Details">
    Enter a **name**, optional **description**, and **tags** for organization. Set the **estimated duration** to help plan timelines. Click **Create Template** before adding phases manually.
  </Step>
  <Step title="Add Phases">
    Click **Add Phase** to create workflow stages. Each phase represents a logical grouping of tasks (e.g., "Discovery", "Setup", "Training", "Go Live"). Drag phases to reorder them.
  </Step>
  <Step title="Add Tasks to Phases">
    Click **Add Item** within a phase to create tasks. Configure each task's type, ownership, and evidence requirements.
  </Step>
  <Step title="Save">
    Use **Save Changes** for template details. Phase and item changes save separately as you work; wait for them to finish before leaving or creating a portal.
  </Step>
</Steps>

## Understand what saves

| Change | When it persists |
| --- | --- |
| New template details | **Create Template** |
| Existing name, description, tags, duration, invitation template, and portal display defaults | **Save Changes** |
| Add a phase | **Add Phase** creates it immediately |
| Phase edits, item fields, and ordering | Their controls save separately; text changes can save after you pause |
| Dependency selection | Selecting or removing the dependency saves it |
| Accepted AI changes | **Apply** writes the accepted changes |
| Linked dates and pages | Their own add/edit/remove controls |

The header save button is not a commit or undo for the entire builder. If an item save fails, stay on the page, record the error, and verify the saved result before launching a portal. A new item needs a title before it can be saved.

## Phases

Phases are the major stages of your onboarding workflow. Their order organizes the workflow and progress display. Configure dependencies where one item must wait for another; ordering alone is not a substitute for a dependency.

Each phase has:

- **Name** — A descriptive label (e.g., "Network Discovery", "Migration", "Training")
- **Description** — Optional details about the phase's purpose
- **Order** — Drag to reorder phases within the template
- **Estimated Duration** — Expected time to complete

<Tip>
Keep phases high-level (3–6 per template works well). Use tasks within phases for the detailed steps.
</Tip>

## Task Types

Each task can collect a specific type of evidence or require a particular action. Set the **evidence type** when creating a task.

### Standard Task

A basic task with optional text evidence. The assignee marks it complete, optionally providing notes.

**Use for:** General action items, internal setup steps, verification tasks

### Meeting

Schedule a meeting directly from the task. Generates calendar invitations with ICS attachments and sends email invitations to selected attendees.

**Use for:** Kickoff calls, discovery sessions, training walkthroughs

### Document Upload

Request specific documents from the client. Documents go through an upload → review → approve/reject workflow.

**Use for:** Insurance certificates, network diagrams, vendor contracts, existing IT documentation

### Digital Signature

Collect a digital signature from the client using a built-in signature pad. Optionally attach a PDF document for the client to review before signing.

**Use for:** Service agreements, acceptable use policies, authorization forms

### Credential Handoff

Securely collect credentials from the client. Supports two modes:

- **Single mode** — Username, password, API key, and notes fields
- **Bulk mode** — Text paste or file upload for multiple credentials at once

Use [Retrieve onboarding credentials and secure files](/user-guides/client-onboarding/retrieve-secure-submissions) for the consuming retrieval controls. Revealing a credential is not a reusable preview.

**Use for:** Admin passwords, VPN credentials, vendor logins, API keys

### Secure File Drop

Requests a separate secure-file submission. MSP staff retrieve it through **Download & Destroy**; this consumes the stored submission. See the [secure retrieval guide](/user-guides/client-onboarding/retrieve-secure-submissions) before using it.

**Use for:** Sensitive configuration files, license keys, security certificates

### Training

Embed training content directly in the task. Supports two modes:

- **Video mode** — Embed videos from YouTube, Vimeo, or Loom with auto-parsed embed URLs
- **In-person mode** — Instructions for scheduled training sessions

**Use for:** Security awareness training, platform walkthroughs, tool-specific training

### Form

Attach a reusable onboarding form so clients submit structured, typed answers inline within the portal. Build forms once in **Settings > Onboarding > Forms** with fields like short text, select, date, email, and number, and optionally map answers into Hudu or IT Glue. You can override whether a specific task allows multiple form entries. If no form is attached, the task falls back to linking a survey from your Surveys module.

**Use for:** IT environment questionnaires, user inventories, site/location inventories, needs assessments

See the [Onboarding Forms guide](/user-guides/client-onboarding/forms) for building and mapping forms.

### Approval

Request a formal approve/reject decision from the client. Optionally attach a supporting document for context.

**Use for:** Budget approvals, scope sign-offs, design approvals, change requests

### Checklist

Attach a checklist template with granular sub-items. Both MSP staff and clients can check off individual items.

**Use for:** Server setup verification, workstation deployment steps, migration readiness checks

### Document Link, Email, Report, and Access Verification

The item picker also offers **Document Link**, **Email**, **Report**, and **Access Verification**. Use a document link for an existing reference; configure the required link instead of expecting an upload request. Email and report items require their selected templates and timing settings. Review recipient roles and client visibility before enabling automatic actions. Access verification is a dedicated access-check workflow; do not substitute a generic completion checkbox for its requirements.

## Task Configuration

Beyond the evidence type, each task has several configuration options:

| Setting | Description |
|---------|-------------|
| **Title** | The task name displayed to both MSP and client |
| **Description** | Detailed instructions or context |
| **Owner** | Who is responsible: **MSP** (your team) or **Client** |
| **Visible to client** | Whether the item is shown in the client portal; separate from ownership |
| **Priority** | Low, Normal, High, or Critical |
| **Due Date Logic** | Offset from phase start, portal start, or dependency completion |
| **Dependencies** | Block this task until another task is completed |
| **Category** | Optional tag for organizing tasks |
| **Milestone** | Flag important tasks as milestones |

### Task Dependencies

Tasks can depend on other tasks. A dependent task appears as "blocked" until its prerequisite is completed. This ensures tasks execute in the correct order.

<Steps>
  <Step title="Open the Dependency Picker">
    When editing a task, click **Add Dependency**.
  </Step>
  <Step title="Select Prerequisites">
    Choose one or more tasks from any phase that must complete before this task unblocks.
  </Step>
  <Step title="Check the saved selection">
    Each selection saves immediately. The task is blocked in the portal until its prerequisites are met. If a circular dependency is rejected, change the selection.
  </Step>
</Steps>

### Task Ownership

Each task is owned by either the **MSP** or the **Client**:

- **MSP tasks** are managed by your team; visible items can appear in the provider progress section.
- **Client tasks** request client action, subject to the item visibility, contact-role, and portal display settings.

Ownership does not guarantee visibility to every contact. Review the portal as the relevant role or contact before activation.

## Documents, Surveys, and Approvals

In addition to tasks, phases can contain:

- **Documents** — Specific files to request from clients (with allowed file type restrictions)
- **Surveys** — Linked survey templates from the Surveys module
- **Approvals** — Formal approve/reject items with optional supporting documents

These appear in dedicated sections of the client portal alongside tasks.

## Client Pages

Templates can also reference **Client Pages** — reusable, read-only reference pages (welcome notes, support instructions, security FAQs) that clients read inside their portal. In the template builder, open the **Client Pages** section and use **Select custom page** to link pages from your library. Each linked page has a **Visible to client portal** toggle so you can keep a page attached but hidden.

Pages are referenced, not copied — update a page once in the library and every template that links it stays current. See the [Client Pages guide](/user-guides/client-onboarding/pages) for details.

## Template Dates

Define standard milestones on the template using **day offsets** from the portal start date. For example, "Kickoff = day 0, Hardware = day 14, Go-Live = day 45". When you launch a portal, the offsets resolve to real dates automatically, and you can mark one as the portal countdown.

Open the **Template dates** section in the builder to add dates with a label, optional description, and **Offset from portal start (days)**. Leave the offset blank to require the admin to set that date manually on each portal. See [Custom Dates and Countdowns](/user-guides/client-onboarding/custom-dates) for how dates appear on a live portal.

## AI Template Designer

Generate complete onboarding templates using AI. Describe your onboarding process in plain language and AI creates the phases, tasks, and structure for you.

The AI designer is a sidebar inside the template builder. It uses the template currently open in the builder. Availability depends on your access and the available AI service. Open a template, select **Assistant** (or **AI Designer** where shown), and describe the change.

<Steps>
  <Step title="Open the AI Sidebar">
    In the template builder, open **Assistant**, or use the **AI Designer** control where shown, to open the design conversation.
  </Step>
  <Step title="Describe Your Process">
    Type a description like "Create an onboarding template for a 50-person law firm migrating from on-prem Exchange to Microsoft 365" or "Add a security hardening phase with MFA enrollment and endpoint protection tasks."
  </Step>
  <Step title="Review the Diff">
    AI generates proposed changes shown in a diff preview. Review each change — added phases, tasks, and configuration.
  </Step>
  <Step title="Apply or Adjust">
    Click **Apply** to persist the accepted changes, or continue the conversation to refine them first. Review removals and dependencies carefully. If an application reports a partial failure, inspect the saved template before retrying; do not assume every change was rolled back.
  </Step>
</Steps>

<Tip>
The AI designer works best when you provide context about the client type, size, and specific requirements. You can also ask it to modify an existing template — for example, "Add a compliance documentation phase after the migration phase."
</Tip>

<Note>
The AI designer is a build tool for your team. It shapes the template while you're editing it, and the result is the saved template your clients receive. Clients never interact with the designer itself.
</Note>

## Testing a Template

Templates don't have a preview of their own, because what a client sees depends on the portal built from the template. To test one:

<Steps>
  <Step title="Create a Draft portal">
    Pick a test or internal company, open its **Onboarding** tab, click **Start Onboarding**, and choose your template. The portal is created in **Draft**. Review configured automation first, and skip project creation or ticket creation when you only need a presentation preview.
  </Step>
  <Step title="View as a contact or role">
    On the portal's **Overview** tab, click the **View as** dropdown and select a contact. With no contacts added, select a client **role** instead. The portal opens in a new tab in read-only preview mode.
  </Step>
  <Step title="Adjust and repeat">
    Fix anything that reads wrong, save the template, and create a fresh Draft portal to see the change. Existing portals keep the structure they were created with.
  </Step>
</Steps>

See [Previewing as a Client](/user-guides/client-onboarding/managing-portals#previewing-as-a-client) for details.

## Import & Export

Share templates across tenants, back them up, or build them in a spreadsheet using the **Import / Export** button in the template builder. The dialog has two formats:

<Tabs>
  <Tab title="JSON">
    JSON carries the exported template structure, including phases, tasks, documents, approvals, and client page data. Review linked library items and configuration after import; an export is not a backup of portal progress, submitted files, or external provider records.

    - **Export JSON** downloads the full template.
    - **Select JSON File** then **Import Template** validates the file and **updates the current template in place**. A preview shows the phase, task, document, and page counts before you import.
  </Tab>
  <Tab title="CSV">
    CSV gives you a flat task table that's easy to edit in a spreadsheet.

    - **Export CSV** downloads the tasks as a spreadsheet.
    - **Select CSV File** then **Import as New Template** **creates a brand-new template** (named after the original with "(imported)" appended) rather than overwriting the current one.
  </Tab>
</Tabs>

## Checklist Templates

Checklist templates are reusable sets of sub-items that can be attached to any task.

<Steps>
  <Step title="Navigate to Checklists">
    Go to **Settings > Onboarding > Checklists**.
  </Step>
  <Step title="Create a Checklist">
    Click **New Checklist**, give it a name and description, then add individual items with labels and ordering.
  </Step>
  <Step title="Attach to Tasks">
    When configuring a task in the template builder, select a checklist template. The checklist items will appear as checkable sub-items within the task.
  </Step>
</Steps>

## Template Management

### Archiving Templates

Archive templates you no longer need. Archived templates are excluded from new portal selection. In the template list, find the archived template and use **Restore** when you need it again. Existing portals using archived templates are not affected.

### Duplicating Templates

Duplicate a template to create a variant. Click the **⋯** menu on any template and select **Duplicate** to save a new copy and open it for editing. Review its linked library content before treating it as an independent version of every form or page.

### Change History

The template builder provides a **Change History** panel for recorded template changes. Open the **Change History** panel to see what changed, who changed it, and when — phase and task additions, edits, and reorders; document, approval, survey, and checklist links; automation changes; and duplication, archive, or restore actions. Hover any entry for the exact timestamp, and use **Load More** to page through older history.

## Best Practices

<AccordionGroup>
  <Accordion title="Keep templates focused">
    Create separate templates for different client types (e.g., "SMB Onboarding", "Enterprise Migration", "M365 Setup Only") rather than one massive template with optional phases.
  </Accordion>
  <Accordion title="Use dependencies strategically">
    Only add dependencies where order truly matters. Over-blocking tasks creates unnecessary bottlenecks for clients.
  </Accordion>
  <Accordion title="Balance MSP and client tasks">
    Don't put all the work on the client. Include MSP-owned tasks so clients can see your team's progress too — it builds trust and transparency.
  </Accordion>
  <Accordion title="Add clear descriptions">
    Write task descriptions from the client's perspective. Instead of "Provide AD credentials," write "Please provide your Active Directory administrator username and password so we can begin the migration."
  </Accordion>
  <Accordion title="Use the AI designer for first drafts">
    Start with AI to generate a baseline template, then customize it to match your exact process. This is much faster than building from scratch.
  </Accordion>
</AccordionGroup>

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Why can I not add a phase to a new template?">
    Enter a name and click Create Template first. A phase needs a saved template.
  </Accordion>
  <Accordion title="Does Save Changes save everything in the builder?">
    No. It saves template details and display defaults. Phases, item fields, ordering, dependencies, dates, pages, and AI application have separate persistence controls.
  </Accordion>
  <Accordion title="Can I cancel item edits by leaving without saving?">
    Do not rely on that. Item changes can already have saved after you pause. Reopen the item to verify its stored values and deliberately correct them if necessary.
  </Accordion>
  <Accordion title="Does changing the template update existing portal tasks?">
    No. Existing portals retain their copied phases and tasks. Create a fresh draft to review a new structure. Shared page content can still be linked to the library.
  </Accordion>
  <Accordion title="Does Apply only preview the AI suggestion?">
    No. Review the proposal before Apply; applying persists accepted changes. A partial failure requires checking the actual saved template before a retry.
  </Accordion>
  <Accordion title="Does importing JSON create a separate template?">
    The builder JSON import updates the current template. CSV Import as New Template creates a separate template. Check the selected format and destination before importing.
  </Accordion>
  <Accordion title="Are MSP-owned tasks automatically hidden from clients?">
    No. Ownership and visibility are separate. Check Visible to client and the portal display settings, then review the relevant contact or role preview.
  </Accordion>
  <Accordion title="Does archiving a template archive its existing portals?">
    No. Template archiving removes it from future portal selection. Existing portals have their own lifecycle and archive actions.
  </Accordion>
</AccordionGroup>
