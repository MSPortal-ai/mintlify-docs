Use this reference to find the MSPortal MCP tool for a job, see what permission it needs and learn whether it changes data. It is for API consumers and MSP staff who have already connected an AI client. If you have not, follow [Connect your client](/user-guides/mcp-server/index) first.

## Before you start

- Connect your client and approve access. See [MCP Server](/user-guides/mcp-server/index).
- Call **get_current_user** to check the connected user, tenant and company.
- Your client receives only the tools that your server version, approved areas, role, company scope, integrations and client tool selection allow. A tool in this reference may not be in your session.
- The catalog groups 383 operations into 120 public tools, so full access stays under a 128-tool client limit.
- Some actions also need a feature turned on for your tenant. Their description ends with the feature they need, such as "Needs the Budget approvals feature." Without it, the action is not in your session.

## Call a read tool

<Steps>
  <Step title="Pick the public tool">
    Find your operation in the tables below. The **Public tool** column is the name your client lists in `tools/list`. The **Action / legacy name** column is the value for `request.action`.
  </Step>
  <Step title="Send the action and its arguments">
    Call the `query_*` tool with `request.action` and `request.arguments`. For example, to list Planner items:

    ```json
    {
      "request": {
        "action": "list_planner_items",
        "arguments": { "page": 1, "limit": 25 }
      }
    }
    ```
  </Step>
  <Step title="Check the result">
    Look for pagination and truncation fields in the response. One page is not the whole data set. Find record IDs with list or search tools. Do not invent IDs.
  </Step>
</Steps>

Each action has its own argument schema and access checks. Use the schema your connected server returns. Seeing a grouped tool does not grant every action in it.

## Change data with a proposal

<Steps>
  <Step title="Request the change">
    Call the `manage_*` tool with the action and its arguments, without `confirm`. MSPortal returns a proposal, a `confirmationId` and an expiry. Nothing is saved.
  </Step>
  <Step title="Review the proposal">
    Check the preview, company, records and effects with the person who asked for the change.
  </Step>
  <Step title="Confirm the same action">
    After approval, call the same tool and action with `confirm: true` and the returned `confirmationId` inside `request.arguments`. For a `manage_planner` proposal with action `create_planner_item`:

    ```json
    {
      "request": {
        "action": "create_planner_item",
        "arguments": {
          "confirm": true,
          "confirmationId": "REPLACE_WITH_RETURNED_CONFIRMATION_ID"
        }
      }
    }
    ```
  </Step>
  <Step title="Check the record">
    Open the new or changed record to confirm the result.
  </Step>
</Steps>

Do not resend changed values on a confirmation call. Request a new proposal to change the target or payload. A proposal expires after ten minutes.

## Tool naming

- **`query_*`** tools read related records or summaries, such as `query_planner` or `query_projects`.
- **`manage_*`** tools stage and confirm related changes, such as `manage_planner` or `manage_meeting_participants`.
- **Standalone tools** keep their names and original arguments, with no `request` wrapper. They are `get_current_user`, `search_portal`, `submit_feedback`, `draft_compliance_notes` and `mark_notification_read`.

## Existing connections and legacy names

Legacy operation names are still accepted by `tools/call` with their original arguments and result shapes. Existing connections keep their OAuth grants and access limits. You do not need a new server URL or grant.

Pending confirmations keep their original operation identity. A proposal can be confirmed through its legacy tool name or the matching grouped action, with the same user, client, expiry and replay checks. The compatibility aliases `update_compliance_status` and `list_compliance_templates` work when called directly but are not listed in `tools/list`. A confirmation created through an alias must keep using that alias.

<Warning>
`tools/list` now returns grouped names, not every legacy operation name. Cached legacy calls still work. Update any client tool-name allowlist to include the public tool names you need. A custom client that requires a legacy name in `tools/list` must update its discovery logic.
</Warning>

## Read the access column

- **Read** retrieves data and needs no proposal. The results still go to your connected client.
- **Write (confirm)** stages a proposal. A proposal is not a saved record. Commit it with the confirmation call.
- **Immediate action** runs with no proposal step. **mark_notification_read** changes your notification state. **draft_compliance_notes** generates output and does not save it.
- **Send feedback** sends a feedback message to MSPortal at once. It is for MSP staff only and needs an explicit user request.

The module scopes below are a summary. You do not need to grant every scope. Read and write grants are separate. The **Permissions** column lists alternatives unless it says **All**. Staff-only gates and record-level checks apply to administrators too. A client-side tool allowlist cannot widen server access.

### Saved notes and Autotask reply status failures

After `add_ticket_note` commits, `posted: true` means the note was saved, even if `statusUpdate.success` is `false`. Do not call `add_ticket_note` again to recover from a status failure.

When `statusUpdate.retry` is present, call `manage_tickets` with action `retry_ticket_reply_status` and the unchanged receipt in `request.arguments.retry`. Review and confirm that proposal using the [normal confirmation flow](#change-data-with-a-proposal). The receipt expires after 24 hours; the confirmation proposal has its own ten-minute expiry.

Retry checks current ticket access and the integration's reply setting. It can skip the status change if the live ticket status or configured target changed, or the setting was disabled. The default closed-ticket policy still applies. Inspect the returned `statusUpdate` result; `noteSaved: true` confirms the existing note, not that the status changed.

If no receipt is returned or it has expired, report that the note is saved and ask the IT provider to check the status. The [Autotask reply setting](/user-guides/integrations/enable-autotask-integration#set-the-status-after-a-client-comment) applies only to company users' public notes, not staff or internal notes.

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Why does my client list fewer tools than this reference?">
    The tables list operations, which are grouped into 120 public tools covering 383 operations in the full catalog. Feature-gated actions, your deployed server, consent scopes, permissions, company access, integrations and client filters can reduce that set further. The reference is not a grant of access.
  </Accordion>
  <Accordion title="Does Read mean a tool can never send anything?">
    No. Tool results go to your connected client. submit_feedback is a separate sending action, is not marked read-only in the consolidated catalog, and needs an explicit request to send feedback.
  </Accordion>
  <Accordion title="Do all writes require a server confirmation?">
    No. Proposal tools stage a confirmation, but immediate actions run directly. Read the access column and exact tool description before authorizing a call.
  </Accordion>
  <Accordion title="Can a confirmation change its target or payload?">
    A confirmation applies the staged proposal. If you want a different target or change, request a new proposal and review it. Do not reuse an old confirmation for a new request.
  </Accordion>
  <Accordion title="Does a successful tool response mean every background job finished?">
    No. Some operations return after scheduling work. Verify the saved record, job status or provider result appropriate to that tool.
  </Accordion>
  <Accordion title="Does list_compliance_templates list reusable run templates?">
    No. It is an alias for check definitions. Use list_compliance_run_templates for reusable run templates and resolve the appropriate records before starting a run.
  </Accordion>
</AccordionGroup>
