Open **Settings > Projects** to configure the Projects area. The unified page has three top-level tabs:

| Tab | Sections |
| --- | --- |
| **Project Settings** | **Display Configuration**, **Client project access**, **Task types**, **Kanban Board Settings**, **Status Mapping**, **Custom Fields**, **Project Types**, and **Upcoming projects** when available |
| **Templates** | **Templates**, **Checklists**, and **Forms** |
| **Client Portals** | **Portals**, **Client roles**, **Pages**, and **PSA projects** when a supported PSA is active |

The default destination is **Project Settings > Display Configuration**. Your role controls the sections available to you. Existing saved links continue to select their destination.

## Before you start

Project configuration requires project-settings read access to view and write access to change. The shared Templates and Forms libraries accept the relevant project-settings or onboarding-settings permission; Client Portals and checklist administration retain their onboarding-settings requirements. PSA-specific selectors depend on the integrations and definitions available in your tenant.

<Warning>
**Client project access**, **Display Configuration**, **Kanban Board Settings**, and **Status Mapping** share the header **Save** button. Project types, templates, forms, client portal sections, and custom fields use their own save behavior.
</Warning>

## Task types and individual task controls

<Note>Branch preview: the filterable Task types table requires the completed Projects update. The instructions below describe the intended post-rollout workflow.</Note>

Open **Project Settings > Task types** to filter synced types by **Task Name**, **Board**, **Internal only**, or **Include in scheduling**. Each switch saves immediately; it does not use the header Save button. Type defaults apply to existing and future tasks of that type, while individual overrides are preserved.

**Internal only** hides a task from company users throughout MSPortal. **Include in scheduling** controls whether it appears in schedules, Gantt, and planning timelines. Turn a switch back to reverse the setting. Excluded tasks retain their saved dependency links, which remain inactive until scheduling is enabled again. These controls do not change the source PSA record.

For an individual task, open its **Visibility and scheduling** controls from the project task view. Changes save immediately. **Use type default** removes an individual override so the current type default applies. If no synced task types appear, individual task controls remain available.

## Project Types

Create an MSPortal type with **New project type**, enter its name, choose **Onboarding**, and select **Create**. Native types can be renamed through **Project type actions > Edit**. PSA types appear from your synced project data.

The **Onboarding** switch saves immediately. It marks the type for the onboarding workflow; selecting that type in a template exposes client portal, pages, dates, and invitation settings. A template with no type keeps the onboarding default. Plain project types expose ticket defaults and the project actions register without portal-only configuration.

Use **Archive** to remove a type from new template choices. Change the table's **Status** filter to find archived types and use **Restore**. Existing records retain their saved type.

## Templates and checklists

Open **Templates > Templates** for the shared project/onboarding template library. Choose **New Template**, set the project type, and create the template before adding its structure. Metadata uses **Save Changes**; phases, items, and named actions save through their individual editors. See [Project Templates](/user-guides/projects/templates) and [Onboarding Templates](/user-guides/client-onboarding/templates).

**Templates > Checklists** holds reusable checklist definitions. Checklist library access still depends on onboarding-settings permissions.

## Forms

Open **Templates > Forms** to maintain reusable form definitions. Both staff and clients can fill forms from a project's **Forms** tab, including ordinary projects without an onboarding portal. See [Project Forms](/user-guides/projects/forms) for Save progress, Submit, sharing, and response links. Staff explicitly share each form before clients can access it. After the archived-response update is rolled out, existing permitted responses to archived forms open with **View** and cannot be edited or resubmitted. Archiving does not change client sharing or response ownership. Onboarding clients can also continue filling forms attached to portal tasks. See [Forms](/user-guides/client-onboarding/forms).

In the role editor, Projects includes separate **View forms and permitted responses**, **Submit and edit form responses**, and **Share forms with clients** permissions. Sharing is a staff operation. Give client roles view and submit permissions as needed; project/company access still applies. General project write access does not automatically grant these granular controls after a role is edited.

Each person can also use **Customize view** in a project to arrange destinations within each section. Personal navigation preferences do not change the access rules configured here.

## Client Portals

This tab requires onboarding-settings access and groups **Portals**, **Client roles**, **Pages**, and, when a supported integration is available, **PSA projects**. Each section keeps its own controls and save behavior. These are reusable settings and the portal directory; manage an individual portal from **Overview > Dashboard > MSP Dashboard** and **Overview > Client Portal** in its linked project.

## Client project access

This tab controls which projects company users can see. MSP staff continue to use their own permitted project scope.

<img src="/images/product/projects-settings-access.png" alt="Client project access choices and active/inactive project health status controls" width="1900" height="1440" />

| Mode | Behavior |
| --- | --- |
| **All projects** | Show the projects otherwise available to each company user. |
| **Filtered projects** | Show projects matching at least one selected project type, line of business, board, or specific project. |

<Steps>
  <Step title="Choose Filtered projects">
    Select **Filtered projects** to reveal the available selectors.
  </Step>
  <Step title="Select the projects to include">
    Choose **Project types**, supported **Project boards** or **Lines of business**, and/or **Specific projects**. Use the searchable project selector for individual projects. Autotask uses lines of business rather than project boards.
  </Step>
  <Step title="Save the access rules">
    Select **Save** in the header. Review the result using the intended client role and company scope.
  </Step>
</Steps>

<Warning>
Filtered projects with no selections gives company users no projects. Individually hidden projects remain hidden even when they match an inclusion filter. Global search follows the same project access rules.
</Warning>

### Project health status

On the same tab, mark each exact PSA status **Active** or **Inactive**. Inactive statuses are excluded from health KPIs and **Projects needing attention**. New PSA statuses start as active.

Use this to exclude statuses that should not participate in portfolio health. It does not change the project's PSA status, replace client access rules, or configure Kanban column mappings. Select **Save** to apply changes.

### Chat with the project manager in Teams

<Note>
Branch preview: this setting is part of the upcoming Projects update. Saving the setting is awaiting rollout verification; the [contact guide](/user-guides/projects/manage-project-contacts#chat-with-the-project-manager-in-teams) shows the local icon preview.
</Note>

**Chat with project manager in Teams** is off by default. Enable it under **Display Configuration**, then select **Save** to make a small Teams icon available beside **Project Lead** in a project's **Overview > Dashboard > Client Dashboard > Contacts**. Turn the switch off and save to hide it again.

The shortcut uses the project manager's existing email address, which must match their Teams sign-in address. It stays hidden when no valid address is available. Clients still need access to the project, and Teams must permit them to chat with the manager.

## Kanban Board Settings

Enable **Kanban Board** to make the ticket board available on eligible project workspaces. Configure **Kanban technicians** to determine the technician columns and assignable roster.

<img src="/images/product/projects-settings-kanban.png" alt="Kanban Board Settings with technician column modes, PSA groups, and specific technician selectors" width="1900" height="1560" />

| Setting | Behavior |
| --- | --- |
| **Only technicians with tickets** | Show Unassigned and the technicians who own project tickets. **Assign to…** opens the picker for another eligible technician. |
| **Everyone in the roster** | Show every assignable technician, including those without tickets on the project. |
| **PSA groups** | Include technicians belonging to any selected supported role, department, team, or line of business. |
| **Specific technicians** | Also include the selected technicians, regardless of group membership. |

Leave both roster selectors empty to allow every active PSA agent. ConnectWise projects remain limited to their ConnectWise project team; roster settings can narrow that team further. Save the settings when finished.

## Status Mapping

Configure **Project Statuses** and **Ticket Statuses** separately. The first organizes whole projects; the second organizes tickets inside project Kanban.

<img src="/images/product/projects-settings-statuses.png" alt="Status Mapping with raw PSA status mode, unmapped statuses, and configurable project groups" width="1900" height="1600" />

<Steps>
  <Step title="Choose raw statuses or groups">
    Enable **Use Raw PSA Statuses** to display original PSA names. To group statuses, keep it disabled and review the configured columns.
  </Step>
  <Step title="Place unmapped statuses">
    Use **Assign** beside an unmapped status, or drag it into a group. **Smart Match** helps place remaining unmapped statuses; review its result. You can also use **Generate with AI** and review the generated mappings before saving.
  </Step>
  <Step title="Review columns and defaults">
    Add or rename groups as needed. Where a default status is configured, it determines the destination used for a board move; otherwise a move can require a status selection. A status belongs to one group at a time.
  </Step>
  <Step title="Save the mappings">
    Check both Project Statuses and Ticket Statuses, then select **Save**.
  </Step>
</Steps>

<Warning>
Check the **Unmapped Statuses** warning before saving. Grouped views can omit items whose PSA status is not mapped. **Clear All** clears the current mapping configuration; review it before saving.
</Warning>

## Custom Fields

Add supported ConnectWise, Halo, or Autotask custom fields and decide where they appear and who can access them.

<img src="/images/product/projects-settings-custom-fields.png" alt="Custom Fields settings showing provider sync status and configured project fields" width="1900" height="1680" />

<Steps>
  <Step title="Check field definitions">
    Review the provider's last sync. Definitions refresh daily. Use **Sync now** after changing definitions in your PSA and wait for the sync result.
  </Step>
  <Step title="Add a field">
    Under **Project fields** or **Project ticket fields**, select **Add field** and search the available PSA definitions. Open an added field to configure it.
  </Step>
  <Step title="Set visibility and access">
    Configure **Show on projects** and, for project fields, **List and filters**. Choose **Who can view** and **Who can edit** using **Staff only** or **Selected roles**. Selected roles with no roles chosen grants no access.
  </Step>
  <Step title="Choose whether to allow PSA edits">
    Enable **Allow edits** only for a supported writable field. An editor also needs field-view access, project edit permission, and the configured field-edit access. Edits to the field value are written back to the PSA.
  </Step>
</Steps>

Project fields appear on the overview and optionally in list columns and filters. Project ticket fields appear when a ticket is expanded under Phases.

<Note>
Changes on Custom Fields are saved immediately. Configure role access before showing a field in project views.
</Note>

## Save, leave, or reset

The header **Save** applies changes across Client project access, Display Configuration, Kanban Board Settings, and Status Mapping. Switching between them lets you continue editing the same unsaved configuration. If you navigate away with unsaved changes, review the app's prompt.

**Reset** replaces those form values with product defaults locally. Review the result and select **Save** to apply it. Reset does not immediately change the saved configuration and does not undo separately saved Custom Fields changes.

## Troubleshooting

| Problem | What to check |
| --- | --- |
| Save is disabled | Your role's write access, whether settings have changed, and whether a save is already running. |
| Clients cannot find a project | Company scope, role permissions, access filters, and whether the individual project is hidden. |
| A project is absent from health KPIs | Its exact PSA status may be Inactive; also check the metric's data requirements. |
| A grouped board omits work | Map the item's PSA status or review raw-status mode. |
| A technician is missing | Active PSA users, roster filters, and the ConnectWise project team. |
| A field is absent or read-only | Definition sync, Show on projects, role access, writeback support, and project permissions. |

## Shared project templates

Use **Templates** to build reusable phases, tasks, decisions, and action items, with optional client onboarding configuration selected by project type. Save a template, then use **Projects > New project** and select **MSPortal only** to create native delivery work. See [Project Templates](/user-guides/projects/templates) and [Native Projects](/user-guides/projects/native-projects). Template changes have their own save action; they do not use the display-settings Save button.
