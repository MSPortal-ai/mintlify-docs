A ticket template can send submitted answers as JSON to an HTTPS workflow you control. Configure the delivery mode explicitly: create a PSA ticket and notify the webhook, or use the webhook as the submission’s only destination.

This is an MSP template-administration task requiring ticket-settings write or manage permission. The receiving workflow may perform its own actions as soon as it receives a request.

## Configure and save

<Steps>
  <Step title="Open the template">
    Go to **Settings > Tickets > Templates**, open the intended template and expand **Flow Recipient (JSON Webhook)**.
  </Step>
  <Step title="Enable delivery and choose its mode">
    Enable the webhook and choose **Create PSA ticket + webhook** or **Webhook only**. Use the actual mode control; clearing individual PSA defaults is not a reliable substitute. Selecting webhook-only delivery also clears incompatible TimeZest scheduling configuration in the editor.
  </Step>
  <Step title="Enter the destination">
    Paste the public HTTPS endpoint and, if used by your receiver, a shared secret. Keep the destination URL and secret private. Local and private-host destinations are rejected.
  </Step>
  <Step title="Test deliberately">
    **Send test event** sends a real HTTP request using synthetic submission values and the current editor configuration. It does not save the template, and the receiving flow can still perform real actions. Use a controlled receiver that handles test events safely.
  </Step>
  <Step title="Save and verify">
    Save the template. Review the saved mode, URL and any affected scheduling settings. For an intended real submission, inspect the recent delivery history and the receiver’s run result.
  </Step>
</Steps>

## Understand the outcomes

| Situation | Outcome to verify |
| --- | --- |
| PSA plus webhook; PSA ticket succeeds | Webhook delivery is separate. Its failure does not roll back the PSA ticket |
| PSA plus webhook; PSA unavailable or creation fails | Inspect the submission result and configured fallback behavior; a webhook response is not proof of a PSA ticket |
| Explicit webhook-only mode | MSPortal sends the submission to the webhook without creating a PSA ticket. A failed webhook returns a submission error |
| Receiver returns HTTP success | The endpoint accepted the request. Its downstream workflow may still fail later |

Do not submit the same real request again solely because a webhook timed out. Check the PSA and receiving system first: either may already have performed work.

## Payload and event names

Current real submissions use **`ticket.submitted`**; synthetic tests use **`ticket.test`**. The envelope includes:

| Property | Contents |
| --- | --- |
| `event`, `timestamp`, `tenant_id` | Event type, timestamp and tenant context; tests use synthetic context |
| `template` | Template ID, name and key |
| `ticket` | Summary, description and available PSA ID, number, URL and routing fields |
| `company` | Company ID, name and external ID when available |
| `contact` | Submitter name, email, external ID and user type when available |
| `fields` | Submitted answers keyed by the template’s field keys |

PSA identifiers can be null. Branch on the actual available identifiers and submission outcome instead of treating an event name as proof that a ticket exists. Allow nullable and optional values in your receiver schema. Use a controlled test payload to configure its parser; real field types depend on the template.

## Verify signatures

When a shared secret is configured, requests include `X-MSPortal-Signature` with a `sha256=` prefix and an HMAC-SHA256 hex digest. Verify it using the same secret over the **raw request body bytes**, before parsing or reserializing JSON. Content type is `application/json`; `X-MSPortal-Event` identifies the event.

A valid signature establishes that the sender knew the secret. It does not by itself prevent replay or establish that the downstream action has not already run. Design duplicate handling in the receiver for operations that must not repeat.

## Inspect delivery history

The saved template’s webhook section can show recent delivery attempts with a timestamp, success/failure, HTTP status, duration and error. Synthetic attempts carry a test badge. Inspect the receiving flow’s history too: MSPortal sees the HTTP result, not completion of every later workflow step.

If a parent template contains embedded templates, review each template’s effective webhook configuration. Embedded submissions can produce their own delivery attempts; test the intended nesting before assuming one user submission means only one request.

## Questions and troubleshooting

<AccordionGroup>
  <Accordion title="Does Send test event save the webhook configuration?">
    No. It sends an actual request using the editor’s current values. Save the template separately before expecting real submissions to use those values.
  </Accordion>
  <Accordion title="Can the test event trigger real downstream actions?">
    Yes. The receiver must distinguish ticket.test and handle it appropriately. Use a controlled test path rather than sending sensitive production data to a public inspection service.
  </Accordion>
  <Accordion title="How do I prevent this template from creating PSA tickets?">
    Select the explicit Webhook only delivery mode and save. Do not rely on clearing individual PSA fields. Recheck any TimeZest scheduling configuration affected by the mode.
  </Accordion>
  <Accordion title="Does webhook-only failure fall back to email?">
    The explicit webhook-only path returns a webhook delivery error. Do not promise email fallback for that mode; inspect the submission result and receiver before retrying.
  </Accordion>
  <Accordion title="Why does my receiver expect ticket.created but receive something else?">
    The current real event is ticket.submitted. Update the receiver’s event handling and schema deliberately, retaining compatibility with any older producers you still use.
  </Accordion>
  <Accordion title="Does HTTP 200 prove my provisioning flow completed?">
    No. It proves the endpoint returned success. Inspect downstream steps and the final created or changed record in the receiving system.
  </Accordion>
  <Accordion title="Why does HMAC verification fail after Parse JSON?">
    Parsing and reserializing can change whitespace or property order. Verify the digest over the raw bytes received, using the same shared secret.
  </Accordion>
  <Accordion title="Should I resubmit after a timeout?">
    Check recent delivery history, the receiver and any PSA ticket first. A timeout does not prove no action occurred, and resubmission may duplicate work.
  </Accordion>
</AccordionGroup>
