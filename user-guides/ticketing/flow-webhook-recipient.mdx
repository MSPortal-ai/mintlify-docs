---
title: 'Flow Webhook Recipient'
description: 'Send each ticket template submission as JSON to Power Automate, Logic Apps, n8n, Zapier, or any HTTPS endpoint, with or without a PSA ticket.'
icon: 'webhook'
---

A ticket template can send a JSON copy of every submission to a webhook URL you control. Use it to start a Power Automate, Logic Apps, n8n, or Zapier workflow, or as the only destination for requests that should never create a PSA ticket, such as HR change requests or approvals.

This guide is for MSP staff whose role can write or manage ticket settings.

## Before you start

- You need an HTTPS endpoint that accepts `POST` requests with `Content-Type: application/json`. For Power Automate, create a flow with the **When a HTTP request is received** trigger.
- The URL must be `https://` and point to a public host. MSPortal rejects localhost, private IP ranges (10.x, 192.168.x, 172.16-31.x), link-local, and carrier-grade NAT addresses.
- The receiving workflow can act as soon as it gets a request, so use a test flow first.

## Set up a webhook

<Steps>
  <Step title="Open the template">
    Go to **Settings > Tickets > Templates** and open the template.
  </Step>

  <Step title="Expand Flow Webhook (JSON)">
    Scroll past **PSA Integration Settings** and click **Flow Webhook (JSON)** to expand it.
  </Step>

  <Step title="Turn on delivery">
    Check **Send submissions to a Flow webhook**.
  </Step>

  <Step title="Choose a Delivery mode">
    - **Create PSA ticket + webhook** creates the ticket as usual and also sends the JSON.
    - **Webhook only** sends the JSON and skips PSA ticket creation.

    Choosing **Webhook only** also clears any TimeZest appointment scheduling on the template, because no ticket exists to schedule against.
  </Step>

  <Step title="Paste the Webhook URL">
    Paste your endpoint into **Webhook URL (https only)**. In Power Automate, copy it from the **When a HTTP request is received** trigger.
  </Step>

  <Step title="Add a shared secret (optional)">
    Enter a random string in **Shared secret (optional)**. Every request then carries an `X-MSPortal-Signature` header your flow can verify. Leave it blank to skip signing. Do not put secrets in the URL.
  </Step>

  <Step title="Send a test event">
    Click **Send test event**. MSPortal posts a `ticket.test` request using your template's field keys with sample values. The company and contact IDs in a test are samples too (`TEST-COMPANY`, `TEST-CONTACT`), so no real client is named. A message such as "Test sent (HTTP 200). Check your Flow run history." confirms delivery. The test does not save the template, and your receiving flow can still take real actions.
  </Step>

  <Step title="Save the template">
    Click **Save Template**. Real submissions use the saved configuration, not the unsaved editor values.
  </Step>
</Steps>

## Send submissions to Rewst

If your tenant has saved a Rewst connection in **Settings > Integrations**, **Flow Webhook (JSON)** shows a **Send submissions to** choice. Choose **Rewst**, then pick a saved connection under **Rewst connection**. Without a saved connection, the choice does not appear.

The trigger URL and secret key stay on the connection, so you do not paste a URL or shared secret on the template. Rewst receives the key in the `x-rewst-secret` header. **Manage Rewst connections** opens integration settings; testing or saving a connection needs permission to manage integrations.

If the selected connection is removed, the template shows **The selected Rewst connection no longer exists.** Click **Custom webhook URL** and enter an endpoint, or pick another connection. Choose **Custom webhook URL** at any time to use your own endpoint with the shared secret described above.

## Test with a request inspector first

A free request inspector such as webhook.site shows exactly what MSPortal sends before you build any flow logic.

<Steps>
  <Step title="Get a unique URL">
    Open [webhook.site](https://webhook.site/). It creates a unique URL for you. Copy it.
  </Step>

  <Step title="Paste it into MSPortal">
    In **Flow Webhook (JSON)**, paste the URL into **Webhook URL (https only)** and check **Send submissions to a Flow webhook**.
  </Step>

  <Step title="Send a test event">
    Click **Send test event**. The request appears in the inspector within a couple of seconds.
  </Step>

  <Step title="Inspect the payload">
    Click the request to see the headers and JSON body. This is the shape your flow receives. Copy the body for the next section.
  </Step>
</Steps>

<Tip>
Save the template and submit a real request with the inspector URL still in place to see a production payload, including the client's PSA company ID. Then swap in your real flow URL. Do not send sensitive production data to a public inspection service.
</Tip>

## Connect Power Automate

<Steps>
  <Step title="Create the flow">
    In Power Automate, create an instant or automated cloud flow and choose the **When a HTTP request is received** trigger.
  </Step>

  <Step title="Save once to generate the URL">
    Power Automate only issues the URL after the flow is saved with the trigger in place. Add a placeholder action, such as a **Compose** with a static value, and click **Save**.
  </Step>

  <Step title="Copy the HTTP POST URL">
    Reopen the trigger and copy **HTTP POST URL**.
  </Step>

  <Step title="Paste it into MSPortal and test">
    Paste the URL into **Webhook URL (https only)**, check **Send submissions to a Flow webhook**, and click **Send test event**.
  </Step>

  <Step title="Generate the schema">
    In the trigger, click **Use sample payload to generate schema** and paste the JSON body you captured. Power Automate then offers `fields.username`, `company.external_id`, and the other properties as dynamic content.

    A schema generated from one sample accepts only that sample's types, and some properties change type between requests. Before you rely on the schema, edit it so these allow both:

    - `company.id`, `company.external_id` and `contact.external_id`: text or `null`.
    - `contact.impersonated_by`: `null`, or an object with `name` and `email`.
    - Every key under `fields` that is optional on the form: its type or `null`.

    In Power Automate, write a nullable property as `"type": ["string", "null"]`, or remove the `type` line for that property. Otherwise **Parse JSON** fails on the first request that sends the other type.
  </Step>

  <Step title="Build the rest of the flow">
    Add the actions you want, such as a SharePoint list item, a Teams message, or a database write.
  </Step>
</Steps>

<Warning>
The Power Automate trigger URL is itself a secret. If the flow provisions, deletes, or changes credentials, set a shared secret in MSPortal and verify `X-MSPortal-Signature` in the first step of the flow.
</Warning>

## Make a webhook-only template

Use this for requests that live entirely outside the PSA.

<Steps>
  <Step title="Set the delivery mode">
    In **Flow Webhook (JSON)**, check **Send submissions to a Flow webhook** and choose **Webhook only**. The **PSA Integration Settings** section is then disabled for the template.
  </Step>

  <Step title="Clear old PSA defaults (optional)">
    If the template still holds a board, priority, or status, open **PSA Integration Settings** and click **Clear PSA defaults** so no stale routing remains.
  </Step>

  <Step title="Enter the URL and save">
    Add the **Webhook URL (https only)**, then click **Save Template**. The **Flow Webhook (JSON)** header shows a **Webhook only** badge.
  </Step>
</Steps>

Webhook-only templates still follow company visibility, role access, and required-field rules. The requester sees **Request submitted** when the workflow accepts the request, and also when it did not answer and MSPortal has queued the request to try again. If the workflow refuses the request, or every attempt fails, MSPortal emails the request to your fallback inbox so it is not lost. See [Retries](#retries).

## Branches

A branch with no webhook of its own sends its requests to the main form's webhook. Set the webhook once on the main form and every client on a branch is covered, including branches you add later.

Open a branch and expand **Flow Webhook (JSON)** to see which applies:

- **This branch uses the main form's webhook** names the delivery mode and where requests go. A change to the main form's webhook applies to the branch too.
- Check **Use a different webhook for this branch** to give the branch its own settings. From then on only the branch's webhook runs for requests made on that branch. The main form's does not, even if you leave the branch's webhook switched off.
- Clear **Use a different webhook for this branch** and save to go back to the main form's webhook.

## What happens on each submission

| Situation | Result |
| --- | --- |
| **Create PSA ticket + webhook**, PSA ticket created | The ticket is created, then the webhook fires. A webhook failure does not undo the ticket. If the workflow does not answer, MSPortal retries. |
| **Create PSA ticket + webhook**, PSA creation fails | The webhook fires once with the submission data. If it succeeds, the requester sees that the PSA ticket failed but the submission went to the webhook. If it also fails, MSPortal emails the request to your fallback inbox right away. |
| **Webhook only** | The webhook fires and no PSA ticket is created. If the workflow does not answer, MSPortal retries, then emails your fallback inbox if every attempt fails. If the workflow refuses the request, MSPortal emails your fallback inbox right away. |
| No PSA integration connected | The webhook is the destination, and failures are handled as in **Webhook only**. |
| Receiver returns HTTP success | The endpoint accepted the request. Its later steps can still fail. |

Each attempt waits up to 10 seconds for a response.

## Retries

MSPortal sends each request once while the person submits. If that attempt fails in a way another attempt can fix, MSPortal tries again on its own:

| Attempt | Sent |
| --- | --- |
| 1 | When the form is submitted |
| 2 | 1 minute after attempt 1 fails |
| 3 | 5 minutes after attempt 2 |
| 4 | 15 minutes after attempt 3 |
| 5 | 1 hour after attempt 4 |
| 6 | 3 hours after attempt 5, about 4 hours 20 minutes after the submission |

- **Retried:** no response within 10 seconds, a connection error, and HTTP 408, 425, 429 or any 5xx.
- **Not retried:** any other 4xx. The receiver refused the request as sent, and the same body would be refused again.
- **Same request every time:** each attempt sends the identical body, with the same `request_id` and `X-MSPortal-Request-Id`, and the same signature. `X-MSPortal-Delivery-Attempt` counts the attempts. If your workflow processed an attempt that MSPortal timed out on, the repeat carries a `request_id` you have already seen, so store that ID and skip a request you have handled.
- **Current settings:** a retry goes to the form's webhook as it is saved at that moment. Fix a wrong URL and save, and the waiting requests reach the corrected URL. Turn the webhook off and a waiting request is treated as failed at its next attempt.
- **When every attempt fails:** a request whose only destination was the webhook (**Webhook only**, or no PSA connected) is emailed to your fallback inbox, the same inbox used when PSA ticket creation fails. A request that also created a PSA ticket is not emailed, because the ticket holds it.

The requester is not asked to do anything while MSPortal retries. Do not submit the same real request again after a timeout: check [Submissions](#list-and-export-submissions) first.

## The JSON payload

<AccordionGroup>
  <Accordion title="Top-level shape">
    ```json
    {
      "event": "ticket.submitted",
      "request_id": "0b1f6c1e-6f0a-4a57-9a4e-2f6d1c0e7b11",
      "timestamp": "2026-05-25T19:45:09.560Z",
      "tenant_id": "...",
      "template": { "id": "...", "name": "...", "key": "..." },
      "ticket":   { "id": ..., "number": "...", "summary": "...", "description": "...",
                    "external_url": "...", "board": "...", "status": "...", "priority": "..." },
      "company":  { "id": "...", "name": "...", "external_id": "..." },
      "contact":  { "name": "...", "email": "...", "external_id": "...", "user_type": "company",
                    "impersonated_by": null },
      "fields":   { "<your_field_key>": ..., "<your_field_key>": ... }
    }
    ```

    Real submissions use `"event": "ticket.submitted"` and your tenant ID. Test events use `"event": "ticket.test"` and the literal tenant ID `"test-tenant"`.

    `request_id` is unique to one submission and identical on every retry of it. Use it to match a request to the [Submissions](#list-and-export-submissions) list and to skip one you have already handled.
  </Accordion>

  <Accordion title="Who the request is for: company">
    | Property | Value |
    | --- | --- |
    | `company.id` | MSPortal's ID for the client company. |
    | `company.name` | The client company's name in MSPortal. |
    | `company.external_id` | The client's company ID in your PSA (ConnectWise, Autotask or HaloPSA), as text. |

    `company.external_id` is filled whenever the client company is linked to a company in the PSA you selected for tickets. It is the same on a main form and on its branches, in both delivery modes, and for requests made by client contacts and by your staff on a client's behalf. It is `null` when:

    - the client company is not linked to a PSA company (check **Settings > Integrations**, your PSA, company mapping);
    - no PSA is connected; or
    - one of your staff submitted the form without choosing a company.

    A client linked to several PSA companies sends the one the requester's own PSA contact belongs to.
  </Accordion>

  <Accordion title="Who sent the request: contact">
    | Property | Value |
    | --- | --- |
    | `contact.name` | The signed-in person's name. |
    | `contact.email` | The signed-in person's own account email. |
    | `contact.external_id` | That person's contact ID in your PSA, as text. `null` when they are not linked to a PSA contact, and for your own staff, who are PSA members and not contacts. |
    | `contact.user_type` | `company` for a client user, `tenant` for your staff. |
    | `contact.impersonated_by` | `null`, unless one of your staff submitted while using **View as**. Then it holds that staff member's `name` and `email`. |

    The contact is never a form answer. MSPortal reads it from the session of the person who submitted, whether they signed in with Microsoft, Google or a password, so someone filling in the form cannot change it. Email addresses a form asks for, such as a new hire's address, arrive in `fields`.

    When one of your staff uses **View as** to act as a client user, `contact` names that client user and `contact.impersonated_by` names the staff member. A workflow that acts on the requester's authority should check that `contact.impersonated_by` is `null`.
  </Accordion>

  <Accordion title="The fields object">
    `fields` uses your template's own field keys. A template with fields `username`, `asset_tag`, and `reason` sends:

    ```json
    "fields": {
      "username": "jdoe",
      "asset_tag": "L-4421",
      "reason": "Forgot password"
    }
    ```

    Every field key in the template is present. Unanswered optional fields are `null`. Multi-select answers arrive as arrays, numbers as numbers, and checkboxes as booleans.
  </Accordion>

  <Accordion title="The ticket object">
    `ticket.summary` and `ticket.description` carry the request's subject and description. `ticket.id`, `ticket.number`, `ticket.external_url`, `ticket.board`, `ticket.status`, and `ticket.priority` are always `null`: the webhook sends the submission, not the PSA ticket made from it. To find the PSA ticket for a request, look the request up in [Submissions](#list-and-export-submissions), where the export lists its ticket number.
  </Accordion>

  <Accordion title="Headers">
    | Header | Value |
    |--------|-------|
    | `Content-Type` | `application/json` |
    | `User-Agent` | `MSPortal-FlowWebhook/1.0` |
    | `X-MSPortal-Event` | `ticket.submitted` or `ticket.test` |
    | `X-MSPortal-Request-Id` | The body's `request_id`, the same on every retry |
    | `X-MSPortal-Delivery-Attempt` | `1` for the first attempt, up to `6` |
    | `X-MSPortal-Tenant` | Your tenant ID, or `test-tenant` on test events |
    | `X-MSPortal-Signature` | `sha256=` plus an HMAC-SHA256 hex digest, only when a shared secret is set |
  </Accordion>
</AccordionGroup>

## Verify the signature

When a shared secret is set, compute `HMAC-SHA256(secret, raw request body)` as lowercase hex, add the `sha256=` prefix, and compare it to `X-MSPortal-Signature`. Use the raw body bytes before you parse or re-serialize the JSON.

A valid signature shows the sender knew the secret. It does not stop a request from being replayed, so make your receiver safe to run twice for any step that must not repeat.

## List and export submissions

Open the saved template and expand **Flow Webhook (JSON)**. **Submissions** lists every request the form sent to the webhook, newest first. A main form includes the requests made on its branches, each marked with its branch name. A branch lists its own. The list updates on its own while a request is waiting for another attempt. A form with no webhook still shows **Submissions** when it has requests to list: those sent before its webhook was turned off, or by a branch that has a webhook of its own.

Each request shows:

- its status: **Delivered**, **Retrying** with the time of the next attempt, or **Not delivered**;
- when it was submitted, the number of attempts when there was more than one, and the last HTTP status;
- the client company with its PSA company ID, and the requester's email;
- the inbox it was emailed to, if delivery failed and MSPortal used the fallback;
- the receiver's error, when there was one; and
- its request ID, the `request_id` your workflow received.

To reconcile against what your workflow received, choose an **Export range** (**Last 7 days** to **Last 12 months**) and click **Export CSV**. The file has one row per request, with these columns in every language:

`request_id`, `submitted_at`, `form`, `branch`, `company_name`, `company_external_id`, `contact_name`, `contact_email`, `contact_external_id`, `contact_user_type`, `summary`, `ticket_number`, `delivery_mode`, `status`, `attempts`, `last_http_status`, `last_error`, `last_attempt_at`, `delivered_at`, `next_attempt_at`, `fallback_email_to`

Times are in UTC. `status` is `delivered`, `retrying` or `failed`. One file holds up to 10,000 requests, the newest first; choose a shorter range if a form has more.

Requests sent before this list existed are included, without a PSA company ID or contact ID. Test events are not requests, so they are not listed here: **Settings > Audit > Ticketing** records them, along with every individual attempt. MSPortal sees only the HTTP result, so also check your receiving flow's run history.

## Embedded templates

If a template contains an [embedded template](/user-guides/ticketing/how-to-create-a-ticket-template#embedded-templates), each template's own webhook fires on its own. The parent's webhook fires for the parent submission, and each embedded template's webhook fires for that embed's ticket. Test the nesting you plan to use. To stop an embed from firing a webhook, leave it unconfigured on the embedded template.

## Troubleshooting

| Problem | What to do |
| --- | --- |
| "Add a webhook URL before testing" | Enter a URL first. |
| Test returns HTTP 4xx or 5xx | The message shows the status and the first part of your endpoint's reply. Check authentication and your flow's schema. In Power Automate, save the flow once after adding the trigger, or the URL returns 404. |
| "Webhook URL must point to a public host" | Use a public hostname. Private, loopback, and link-local addresses are blocked. |
| "Webhook URL must use https://" | Change the URL to start with `https://`. |
| The test arrived but real submissions do not | Confirm the template is active and that you clicked **Save Template** after enabling the webhook. Then submit from **Tickets > New Ticket** and check your flow's run history. |
| Your flow expects `ticket.created` | The current real event is `ticket.submitted`. Update the receiver. |
| HMAC check fails after **Parse JSON** | Parsing and re-serializing changes whitespace and key order. Hash the raw body exactly as received, with the same secret. |
| You need to know if a PSA ticket exists | Open **Submissions** and export the range. `ticket_number` is filled for a request that created a PSA ticket. |
| `company.external_id` is `null` | The client company is not linked to a company in your PSA, or staff submitted without choosing a company. Map the company under **Settings > Integrations**, then submit again. |
| A request shows **Retrying** | Your endpoint did not answer or returned 408, 425, 429 or a 5xx. MSPortal sends it again at the time shown. Fix the endpoint, or correct the URL and save. |
| A request shows **Not delivered** | Every attempt failed, or the endpoint refused the request. The row names the inbox the request was emailed to, and the receiver's error. |

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Does Send test event save my settings?">
    No. It sends a real request using the current editor values. Click **Save Template** before you expect real submissions to use them.
  </Accordion>
  <Accordion title="Can the test event trigger real actions?">
    Yes. Your flow must recognize `ticket.test` and handle it safely. Use a controlled test path.
  </Accordion>
  <Accordion title="How do I stop a template from creating PSA tickets?">
    Choose **Webhook only** and save. Clearing individual PSA fields is not enough on its own.
  </Accordion>
  <Accordion title="Does HTTP 200 prove my provisioning flow finished?">
    No. It proves the endpoint accepted the request. Check the later steps and the final record in the receiving system.
  </Accordion>
  <Accordion title="Should I resubmit after a timeout?">
    No. MSPortal retries on its own, with the same `request_id`. Check **Submissions**, your flow, and the PSA first. A timeout does not prove nothing happened, and resubmitting creates a second request with a new `request_id`.
  </Accordion>
  <Accordion title="Do branches use the main form's webhook?">
    Yes. A branch without its own webhook settings uses the main form's, and keeps following it when it changes. A branch with **Use a different webhook for this branch** checked uses only its own. See [Branches](#branches).
  </Accordion>
  <Accordion title="Can I point several forms at one endpoint?">
    Yes. Use `template.key` to tell the forms apart and `company.external_id` to tell the clients apart. Both arrive on every request.
  </Accordion>
  <Accordion title="Can the person filling in the form change contact.email?">
    No. It is the signed-in person's account email, read from their session. See **Who sent the request: contact** under [The JSON payload](#the-json-payload).
  </Accordion>
</AccordionGroup>
