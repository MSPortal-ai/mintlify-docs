Use this MSP administrator workflow to prepare Halo access before connecting MSPortal. Effective access depends on the API application’s scopes and its selected identity, including role and team restrictions. A dedicated identity makes the integration’s access easier to review; it does not by itself establish minimum required permissions.

## Before you start

You need a Halo administrator who can manage roles, agents and API applications. Decide which companies, teams and features MSPortal should access, including any intended ticket or warranty writes.

Halo versions can offer different application identity controls. Follow [Halo’s current API application guide](https://www.usehalo.com/guides/1823) for your instance. The steps below describe the agent-based setup used in the [MSPortal Halo connection guide](/user-guides/integrations/enable-halo-integration).

## Prepare the role and agent

<Steps>
  <Step title="Create a dedicated role">
    In Halo, open **Configuration > Teams & Agents > Roles**, create an **MSPortal** role and save it. Select the module access required for your chosen integration features. Do not copy a broad administrator or delete-permission list merely to make all optional checks green.
  </Step>
  <Step title="Assign the intended departments and teams">
    Open the role’s **Departments & Teams** settings and add the departments and teams whose records MSPortal should access. Save the changes. Missing team access can produce incomplete results even when authentication succeeds.
  </Step>
  <Step title="Create the API agent">
    Under **Configuration > Teams & Agents > Agents**, create a dedicated MSPortal agent, choose the role and enable the API-only agent option. Save and review its effective permissions. This identity is for the integration; it is not the human assignee you should choose for service work.
  </Step>
</Steps>

## Link the API application

Open **Configuration > Integrations > Halo API**, then the applications list. Create or edit the MSPortal application using **Client ID and Secret (Services)** and select the intended **Agent to Log in as** where your instance uses agent-based authentication.

Review the application permissions as well as the agent role. Keep the client ID and secret in your approved secret store and the MSPortal connection form. Save the application before continuing.

## Verify the required features

Return to MSPortal’s **Settings > Integrations > Halo PSA** setup. For a new integration, **Test Connection** can save the connection on success. Continue to **Permissions**, inspect required and optional results, then configure sync scope and company mappings.

| Result | What to do |
| --- | --- |
| Authentication fails | Check the instance URL, client credentials and application identity |
| Required access denied | Review the named application scope and effective agent access |
| Optional feature denied | Grant it only if that feature is intended; otherwise leave its synchronization disabled |
| Timeout or unverified result | Resolve connectivity or endpoint availability before assuming the role is wrong |
| Connected but records missing | Check team restrictions, saved sync filters, dataset completion and company mappings |

The permission checks establish read access to tested endpoints. They do not prove ticket creation, comments, invoice changes or warranty writeback will succeed. Verify intended writes through their normal workflow and inspect the actual result.

## Maintain access

After changing a role, application scope or team assignment, repeat the relevant permission check and confirm that intended records are visible. Avoid revoking working credentials until you have verified the supported replacement path. Updating a Halo role is not the same as rotating the credentials stored by MSPortal.

## Questions and troubleshooting

<AccordionGroup>
  <Accordion title="Is an API-only agent automatically least privilege?">
    No. Its effective role and application scopes determine access. Review the chosen features and team restrictions; the dedicated identity mainly makes that access explicit.
  </Accordion>
  <Accordion title="Why does authentication pass but some tickets are absent?">
    The agent may lack the relevant team or department access, or MSPortal filters and mappings may exclude those records. Check those boundaries and sync results before broadening permissions.
  </Accordion>
  <Accordion title="Do I need every optional permission?">
    Only enable access for features you intend to use. Required denied access blocks supported setup progression; optional unavailable features can remain disabled.
  </Accordion>
  <Accordion title="Does a green permission test prove ticket writeback works?">
    No. These checks test read access. Ticket creation and updates need the applicable write permissions and a verified result from the actual workflow.
  </Accordion>
  <Accordion title="Should I grant administrator access to fix an unverified result?">
    First inspect the error. Timeout and endpoint failures do not prove a permission denial. Correct the identified problem and retest the affected capability.
  </Accordion>
  <Accordion title="Where do I continue after creating the role?">
    Open the Halo setup wizard in MSPortal, connect the application, review Permissions, select sync scope and complete company/user imports as intended.
  </Accordion>
</AccordionGroup>
