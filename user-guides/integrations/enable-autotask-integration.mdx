This guide walks you through connecting your Autotask PSA instance to MSPortal.ai. MSP staff set up the connection; company users do not administer it. You connect, check permissions, choose data and match records on the Autotask connection page.

MSPortal can also import **Autotask native survey results** into the **CSAT Dashboard**, custom dashboard widgets, report blocks and CSV exports. The import is off by default, and you can keep collecting feedback through Autotask's own surveys. See [Import Autotask native CSAT for dashboards and reports](#import-autotask-native-csat-for-dashboards-and-reports).

## Prerequisites

- Admin access to Autotask, or API credentials (username and secret)
- Admin access to MSPortal.ai with integration management permissions
- The Ticket Settings permission in MSPortal if you will edit ticket defaults

## Part 1: Configure Autotask PSA

Before connecting to MSPortal.ai, you need to create an API user and security role in Autotask. See Autotask's [API user setup](https://autotask.net/help/developerhelp/content/apis/General/Define_API_User.htm) and [REST authentication](https://www.autotask.net/help/DeveloperHelp/Content/APIs/REST/General_Topics/REST_Security_Auth.htm) guides for background.

### Create Security Role

<Steps>
  <Step title="Access Security Settings">
    1. Navigate to [Autotask](https://ww2.autotask.net)
    2. Go to the Admin area
    3. Click **Account Settings & Users**
    4. Click **Security Levels**
  </Step>

  <Step title="Create MSPortal Security Role">
    1. Copy the default **API User (system)** role
    2. Rename it to **MSPortal**
    3. Scroll down to **Other** and enable:
       - **Can create webhooks**: Yes
       - Set webhook limit to **25**

    <Note>
      We recommend setting unused areas to "No permissions" or "Read only" to follow the principle of least privilege. However, this may cause synchronization issues if you later enable those features.
    </Note>
  </Step>

  <Step title="Save the Role">
    Click **Save & Close** to finalize the security role settings.
  </Step>
</Steps>

### Create API User

<Steps>
  <Step title="Navigate to Users">
    1. Go back to **Account Settings & Users**
    2. Select **Resources/Users**
    3. Click to add a new **API user**
  </Step>

  <Step title="Configure API User">
    Fill in the following details:

    | Field | Value |
    |-------|-------|
    | **First Name** | MSPortal |
    | **Last Name** | Integration |
    | **Security Level** | MSPortal (the role you created) |
    | **Email Address** | Use an internal alias for receiving integration logs |
    | **Primary Internal Location** | Select your headquarters |
    | **Integration Vendor** | MSPortal.ai |

    The MSPortal connection form asks only for the API username and secret. It has no field for a custom tracking identifier, so set the integration vendor here. If Autotask rejects the tracking identifier, confirm the vendor association with your Autotask administrator.
  </Step>

  <Step title="Generate API Credentials">
    1. Under **Credentials**, click **Generate Key**
    2. Click **Generate Secret**
    3. **Important:** Save the API username and secret immediately. The secret cannot be retrieved later.

    <Warning>
      Make sure to copy and save your API credentials before closing this dialog. The secret cannot be viewed again after creation.
    </Warning>
  </Step>

  <Step title="Associate Lines of Business">
    Associate the appropriate lines of business with the API user, then click **Save & Close**.
  </Step>
</Steps>

## Project management permissions

Skip this section unless you will create or update Autotask projects from MSPortal. These settings go on the security level of the **API user whose credentials are saved in MSPortal**. A technician's own security level does not give the integration any access.

<Steps>
  <Step title="Open the API user's security level">
    In Autotask, go to **Admin** > **Resources/Users** > **Security Levels** and edit the level assigned to the MSPortal API user.
  </Step>

  <Step title="Grant project access">
    Autotask treats **project tasks** separately from service tickets, so Service Desk ticket access alone is not enough. Set the access below. A custom security level may express some of these through module settings and **Other** options rather than one checkbox per item.

    | Project operation | Required API user access |
    |-------------------|--------------------------|
    | Read the portfolio and project details | **Projects** > **Project: View (All)**, including the intended companies and Lines of Business |
    | Create projects, including from MSPortal templates | Project **Add** access |
    | Update project status, dates and mapped project fields | Project **Edit** access across the intended projects |
    | Read, create and update phases | Query, create and update access to **Phases** through the Projects module |
    | Read, create and update project tasks | Query, create and update access to **Tasks**, including status, primary resource, priority, title, estimated hours, dates and mapped task fields. Do not restrict the API user to tasks assigned to itself. |
    | Read project effort and time entry notes | Query access to **TimeEntries** for the intended project tasks and resources |
    | Log time against project tasks | Create access to **TimeEntries**, the Projects **Can enter time on** setting for the intended tasks, and permission to enter time for the selected resource. Enable the billing field permissions if you set billable or non-billable time. |
    | Populate company, contact and assignment choices | Read access to **Companies**, **Contacts**, **Resources**, **Roles**, **Departments** and the work types and billing codes your tasks and time entries use |
    | Populate statuses, priorities, types and mapped fields | Read access to the project and task picklists and user-defined field definitions |

    Autotask can hide tasks by **Line of Business** even with **View (All)**, so include every Line of Business the integration should see. Baseline project tasks stay read-only, and Autotask's rules for completed tasks and submitted or posted time still apply. See Autotask's [task access rules](https://www.autotask.net/help/Developerhelp/Content/APIs/REST/Entities/TasksEntity.htm) and [time entry requirements](https://ww2.autotask.net/help/developerhelp/Content/APIs/REST/Entities/TimeEntriesEntity.htm).

    Do not grant blanket Delete access or an administrator account. These read, create and update operations do not need them.
  </Step>

  <Step title="Save and re-check">
    Save the security level. In MSPortal, go to **Settings** > **Integrations**, open the Autotask PSA connection, select **Permissions** and click **Re-check**.
  </Step>

  <Step title="Test on a project">
    A green **Projects** result only confirms MSPortal can read projects. Create a test project, edit a task and log time on it to confirm write access. If applying a template partly succeeds, check the records it created before you retry. An Autotask administrator can also inspect the API user's effective access with Autotask's [entityInformation permissions](https://www.autotask.net/help/Developerhelp/Content/APIs/REST/API_Calls/REST_EntityInformationCall.htm).
  </Step>
</Steps>

<Note>
In MSPortal, Autotask project task notes are **time entry notes**. Standalone project task notes and editable checklist items are not available for Autotask, and extra Autotask permissions will not turn them on. MSPortal-only projects and templates use MSPortal permissions only.
</Note>

## Part 2: Connect Autotask in MSPortal

The Autotask connection page lists its setup tasks in the **Setup guide**: **Connect**, **Permissions**, **Choose data**, **Import or match companies**, **Import or match users**, **Import devices**, **Configure tickets**, **Configure opportunities** and **Review**. **Import or match users**, **Import devices** and **Configure opportunities** are optional. Select a task to return to it at any time.

### Open the connection

<Steps>
  <Step title="Navigate to Integrations">
    In MSPortal.ai, go to **Settings** > **Integrations**.
  </Step>

  <Step title="Start Setup">
    Find **Autotask PSA** and select **Connect**. To continue an existing setup, open the existing Autotask PSA connection instead.
  </Step>
</Steps>

---

### Connect

<Steps>
  <Step title="Enter API Credentials">
    Fill in the following fields:

    | Field | Description |
    |-------|-------------|
    | **API username** | Your Autotask API user email (e.g., `api.user@yourdomain.com`) |
    | **API secret** | The API secret generated for your API user |
  </Step>

  <Step title="Test the connection">
    Select **Test connection** and resolve any reported error. A successful test does not save the connection.

    <Note>
      If the connection fails, verify your API username and secret are correct and that the API user has the MSPortal security role assigned.
    </Note>
  </Step>

  <Step title="Save and continue">
    Select **Save and continue** to create the connection, then continue to **Permissions**.
  </Step>
</Steps>

---

### Permissions

MSPortal checks what your Autotask API user is allowed to read, and shows the result for each area of data. If the check has not run yet, select **Run check**.

<Steps>
  <Step title="Review the results">
    Each area of data is listed as **Granted**, **Not permitted** or **Could not verify**.

    Areas marked **Required** must be granted before you can continue: Companies, Contacts and staff, Tickets, and Queues and statuses. Without these the integration cannot function.

    Other areas cover Configurations, Opportunities, Product catalog, Invoices, Contracts, Projects, Time entries, Service calls, Company notes, and Satisfaction feedback. You can continue and fix them later.
  </Step>

  <Step title="Grant anything missing">
    Any area that is not permitted shows the exact security level setting to change, for example **Security Level -> Contracts -> Products & Services: View**.

    Update the security level assigned to your API user in **Admin > Resources/Users > Security Levels**, then come back and click **Re-check**.

    <Note>
      **Could not verify** usually means Autotask was slow or unavailable, not that a permission is missing. Click **Re-check** before you change the security level.
    </Note>
  </Step>

  <Step title="Continue">
    Optional areas that are not granted keep their syncs switched off, and their switches in **Choose data** stay locked until you grant the permission and re-check.
  </Step>
</Steps>

These checks test **read access** only. A green result does not prove that ticket creation, comments, warranty updates or other writes will succeed.

<Tip>
  If a permission is removed later, MSPortal switches off the affected sync and notifies your integration admins rather than retrying against an entity it can no longer read.
</Tip>

### Choose data

Choose what data to sync from Autotask and set up automatic imports. Each switch and filter saves as you change it, so wait for the saved state before you leave. Turning on a dataset reveals its settings directly below it; turning it off hides them without clearing saved choices. Start the initial sync when it is offered. Options in later tasks can stay incomplete while it runs.

<Steps>
  <Step title="Choose datasets">
    | Option | Description |
    |--------|-------------|
    | **Sync Users** | Sync user/contact data from Autotask |
    | **Sync Companies** | Sync company/account data from Autotask |
    | **Enable Ticket Sync** | Sync tickets from Autotask |
    | **Enable Opportunity Sync** | Sync opportunities from Autotask |
    | **Enable Project Sync** | Sync projects from Autotask |
    | **Enable Invoice Sync** | Sync invoices from Autotask |
    | **Sync product catalog** | Import the product and service catalog for quoting and budgets |
    | **Enable configuration item sync** | Sync configuration items into device staging for reporting and import |
    | **Enable change management** | Import Autotask changes into the change calendar |
    | **Import satisfaction ratings** | Import completed Autotask survey results. See [Import Autotask native CSAT](#import-autotask-native-csat-for-dashboards-and-reports). |
    | **Warranty writeback** | Write warranty expiration dates to Autotask configuration items. See [Write warranty dates back to Autotask](#write-warranty-dates-back-to-autotask). |

    <Note>
      A switch appears locked when the permission check found that your API user cannot read that data. Grant the permission named beside it in Autotask, then select **Re-check** in **Permissions** to unlock it.
    </Note>
  </Step>

  <Step title="Configure Contact Auto-Import">
    If you want contacts to be automatically imported when companies are added:

    1. Turn on **Enable Auto-Import** to automatically create user accounts for active contacts
    2. Select a **Default Role for Imported Contacts** (e.g., Viewer)
    3. Optionally, map specific Autotask contact types to other portal roles. Unmapped types use the default role.

    <Tip>
      We recommend choosing a role with minimal permissions (basic ticket creation only) if you plan to import all contacts.
    </Tip>
  </Step>

  <Step title="Configure Company Auto-Import and Filters">
    | Setting | Description |
    |---------|-------------|
    | **Auto-Import Company Types** | Companies of the selected types are created in the portal automatically during sync. MSPortal asks you to confirm before it imports a new batch, because companies are a billed item. |
    | **Exclude Company Types** | Select company types to exclude from sync |
  </Step>

  <Step title="Configure Ticket Sync Scope">
    With **Enable Ticket Sync** on, define which tickets to sync:

    | Setting | Description |
    |---------|-------------|
    | **Sync recurring tickets** | Include tickets generated from Autotask recurring ticket templates |
    | **Queues to Sync** | Select which Autotask queues' tickets to sync |
    | **Exclude Statuses** | Select ticket statuses to exclude from sync |
    | **Categories** | Select the ticket categories to sync, or leave it empty to sync every category. Categories added in Autotask later stay unselected until you add them; the note under the field lists the categories whose tickets don't sync. |
  </Step>

  <Step title="Choose invoice visibility">
    With **Enable Invoice Sync** on, use **Hide invoice statuses** to hide closed, voided or other statuses from the Invoices page. Every invoice still syncs.
  </Step>

  <Step title="Configure Planner Auto-Import (Optional)">
    With **Enable Opportunity Sync** on, turn on **Auto-import opportunities into the Planner** to create a planner item for each new Autotask opportunity. Use **Minimum opportunity value** and **Opportunity types to auto-import** to limit which ones come through. See [Importing PSA Opportunities](/user-guides/planner/index#importing-psa-opportunities).
  </Step>
</Steps>

Synchronizing source records, linking them to companies and importing portal records are separate steps. Automatic company and contact imports can create portal records when matching source records arrive, so review filters and auto-import settings before you turn them on. Check errors and the actual sync result before you treat an empty list as the final dataset.

### Import or match companies

Open **Import or match companies**. Its first view, **Import**, includes unlinked records with or without suggestions; use **Suggested** to review proposed matches.

- Select **Import** beside a source company to import it on its own.
- Select **Import companies** to open the selection dialog. It loads unmatched records across pages for the current search. Use **Select current page** or **Select all pages**, review the names and selected count, then confirm. Existing portal companies with the same name are matched instead of duplicated.
- To link a company that already exists under a different name, choose it in the row, or review and accept the suggested match. **Accept strong matches** accepts every suggestion with 90% confidence or more after you review the list.

Accepted matches, removed matches and ignores save when applied. Opening the import dialog alone saves nothing. See [Import companies](/user-guides/integrations/import-companies) for selection scope and retry guidance.

### Import or match users (Optional)

Import or match at least one company first. You can leave other companies for later and return to import more users.

<Steps>
  <Step title="Select contacts">
    The workspace opens on **Import**, which includes suggested contacts too. Use **Import** beside a contact, or select contacts and choose **Import selected**. Use the header checkbox to select the current page, click it again to select all pages matching the current filters, and click again to clear the selection. **Select all with email** replaces the selection with contacts that have an email address across all pages matching the current filters. Large selections run in batches.
  </Step>

  <Step title="Review and confirm">
    In the review panel, choose the intended Company role and review the ready-to-import and skipped counts. Contacts without an email address are skipped; you can add an address before confirming. Correct invalid addresses or clear them to skip those contacts, and resolve duplicate addresses.
  </Step>

  <Step title="Check the result">
    Read the result and verify the saved users. To link an existing account instead, choose that user or accept a reviewed suggestion. Importing contacts does not invite them to the portal.
  </Step>
</Steps>

Client contacts are imported here. See [Import users](/user-guides/integrations/import-users) for selection scope and retry guidance.

Make sure **Enable configuration item sync** is on in **Choose data**, then open **Import devices** to map configuration item types to MSPortal device types and select the items to import. Confirm the intended company and device type before importing, then check the result in Devices.

### Configure tickets

Set up how Autotask tickets behave in MSPortal. Each change saves straight away. Wait for the saved state and resolve any reported save failure before you leave.

<Steps>
  <Step title="Review new ticket defaults">
    **New ticket defaults** sets the PSA values used for new tickets created in the portal. These are the same defaults as **Settings** > **Tickets**, and editing them requires the Ticket Settings permission.
  </Step>

  <Step title="Choose ticket statuses">
    Under **Ticket statuses**, select the **Closed statuses** that mean a ticket is closed. Status choices appear once queues are chosen in **Choose data**; missing choices can mean the first metadata sync has not finished. To set a status after a company user replies, see [Set the status after a client comment](#set-the-status-after-a-client-comment).
  </Step>

  <Step title="Place statuses in resolution stages">
    **Resolution stages** drive the visual indicator of ticket progress. Place each Autotask status in the stage it belongs to. A status can sit in one stage only.

    | Stage | Description |
    |-------|-------------|
    | **New** | Tickets that are newly created or not yet triaged |
    | **Triaged** | Tickets that have been reviewed and prioritized |
    | **Working** | Tickets actively being worked on |
    | **Waiting** | Tickets waiting for customer response or approval |
    | **Resolved** | Tickets that are completed or closed |
  </Step>

  <Step title="Set Autotask ticket defaults">
    | Setting | Description |
    |---------|-------------|
    | **Fallback Resource** | Assigned when creating tickets without a specific resource. Cannot be an API-only user. |
    | **Default Note Type** | Default note type for ticket comments |
    | **Account Note Action Types to Sync** | Only company notes with these Autotask action types are imported and shown on the company **Notes** tab. Leave empty to sync none. |
  </Step>

  <Step title="Set a reply mailbox for emailed notes (Optional)">
    Emailing ticket notes is off until you turn it on in **Settings > Tickets > General > Email ticket notes**. To let staff and company users email a ticket note on this connection, also set **Reply mailbox** under **Emailing contacts from notes**. Enter the mailbox Autotask reads incoming email from. MSPortal sends the note from your sending domain with this mailbox as the reply address and the ticket number in the subject, so a reply is added to the ticket. Without it, the **Email to** field is not offered on this connection's tickets.
  </Step>

  <Step title="Sync actions">
    | Action | Description |
    |--------|-------------|
    | **Sync tickets now** | Trigger an immediate sync of ticket data |
    | **Clear & Resync** | Delete this integration's synced tickets in MSPortal and perform a fresh sync (useful after major configuration changes). Tickets in Autotask are not affected. |

    See [Clear and Resync Integrations](/user-guides/integrations/clear-and-resync-integrations) before you use **Clear & Resync**.
  </Step>
</Steps>

### Set the status after a client comment

<Note>
  **Branch preview:** These Autotask reply settings and screenshots describe an
  unreleased update. They are not yet verified in production.
</Note>

Use this setting to move an Autotask ticket to a chosen status after a company user successfully saves a public note through MSPortal. MSP staff notes, internal notes and private notes do not trigger it.

You need permission to manage integrations. The Autotask API user also needs permission to create ticket notes and update ticket status; the **Permissions** read checks alone do not prove those writes will succeed.

<Steps>
  <Step title="Open Configure tickets">
    Go to **Settings > Integrations > Autotask PSA**, open the connection you want to change, and select **Configure tickets** in its setup guide.
  </Step>
  <Step title="Choose a reply status">
    Under **Ticket statuses > Status after a client comment**, select an active status from this Autotask connection. Choose **None** to turn the automatic status update off.
  </Step>
  <Step title="Choose what happens on closed tickets">
    **Replies on closed tickets** becomes available after you select a reply status.

    | Choice | Result after a company user's public note |
    | --- | --- |
    | **Keep closed or resolved** (default) | Save the note and leave a closed or resolved ticket's status unchanged. |
    | **Change to reply status** | Apply the selected reply status even when the ticket is closed or resolved. Choose an open reply status if you want replies to reopen tickets. |

    Closed-ticket handling includes statuses marked closed in Autotask, your **Closed statuses**, and statuses placed in the **Resolved** resolution stage.

  </Step>
  <Step title="Wait for each change to save">
    Each selection saves immediately. Resolve any save error before leaving, then reload to confirm the saved choices. To stop automatic status changes later, select **None**.
  </Step>
</Steps>

The setting applies to this integration's tickets. Company overrides are not supported in this release. MSPortal writes only the reply status for this step; it does not write the assigned technician, queue or priority. Autotask workflows may react separately to the status change.

If the note saves but the status update fails, the portal and browser extension tell the company user that the note was saved and offer **Retry status update** when a retry is available. Retrying changes only the status and never posts another note. See [When a reply changes the ticket status](/user-guides/ticketing/follow-up-on-a-ticket#when-a-reply-changes-the-ticket-status).

| Problem                                    | What to check                                                                                                                                                            |
| ------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| No reply statuses are available            | Check this connection's selected queues and metadata sync, then reload. The target must be an active status from this integration.                                       |
| A staff note did not change the status     | Only company users' public notes trigger this setting.                                                                                                                   |
| A closed ticket stayed closed              | **Keep closed or resolved** is the default. Select **Change to reply status** only if replies should apply the chosen status to closed tickets too.                      |
| A note saved but its status did not update | Check the Autotask connection, API user's write access and whether the selected reply status is still active. Retry the status when offered; do not post the note again. |

### Review

Open **Review**, resolve any required incomplete tasks, then select **Finish setup**. Each task saves its own changes, so finishing setup does not apply a separate batch of pending company or user imports. Syncs and imports keep running in the background; check their results separately.

## Managing Your Integration

After setup, open the Autotask PSA connection from **Settings** > **Integrations**:

- **Overview** and **Sync activity**: Check connection status, sync results and errors
- **Setup guide** tasks: Change saved scope, matches and settings
- **Run sync**: Request a manual sync of all data, or one data type
- **More actions** > **Rename**: Label the connection
- **More actions** > **Disconnect…**: Remove the stored credentials, company matches and synced data after confirmation. This cannot be undone. Revoke the API user's credentials in Autotask separately.

To replace the API credentials, open **Connect**, enter the new username or secret, select **Test connection**, then select **Save changes**. Leave masked values unchanged to keep them. A test alone does not save replacement credentials, so confirm the saved connection before you revoke the old credential in Autotask.

### Webhook Management

MSPortal provisions the Autotask webhooks for ticket changes, so no manual webhook setup is required in Autotask. A weekly check re-creates any webhook that has gone missing. If webhooks stop working, verify that your API user's security role still allows creating webhooks, then contact MSPortal support.

## Import Autotask native CSAT for dashboards and reports

This imports survey results already collected by Autotask's built-in surveys. You do not need Simplesat or a new MSPortal survey. The import is off by default.

<Steps>
  <Step title="Grant survey rating rights">
    In Autotask, open **Admin** > **Resources/Users** > **Security Levels** and edit the level assigned to the API user. Under **Other** > **Surveys**, enable **Can view Organization Survey Ratings and Contact Survey Ratings** and **Can view Resource Survey Ratings**.
  </Step>

  <Step title="Re-check permissions">
    In MSPortal, open the Autotask PSA connection, select **Permissions**, click **Re-check** and confirm **Satisfaction feedback** is granted.
  </Step>

  <Step title="Turn on the import">
    Open **Choose data** and turn on **Import satisfaction ratings**. There is no rating scale to choose, because Autotask survey questions rate **1 to 5**. Each completed survey's overall rating is rounded to a whole number on that scale.
  </Step>

  <Step title="Start the first import">
    Wait for the switch to save, then start the sync when it is offered. Later imports run hourly. A saved setting does not mean every response has arrived.
  </Step>

  <Step title="Check company links">
    Make sure the surveyed companies are linked to portal companies and their tickets have synced. A result whose company is not linked will not appear in company-scoped CSAT results until a later sync can resolve it. Technician attribution uses the assigned resource on the synced ticket.
  </Step>

  <Step title="Grant read access">
    Give intended readers **Surveys** > **Read** > **CSAT** in their role. Building dashboards and reports also needs the matching permissions.
  </Step>
</Steps>

Only completed surveys are imported. Surveys that were sent but not answered, and surveys completed without answering any rated question, are not counted. Autotask does not provide free-text survey answers to integrations, so imported responses carry ratings only.

### Present the imported results

| Where | How |
|-------|-----|
| **CSAT Dashboard** | Open **Surveys** > **CSAT Dashboard** to read scores and trends, or export responses. Autotask results are grouped under **Autotask PSA satisfaction**. See [Read and export support satisfaction feedback](/user-guides/surveys/read-csat-feedback). |
| **Custom dashboards** | Add **CSAT Overview**, **CSAT Trend**, **CSAT by Company** or **Recent CSAT Feedback** from the widget library, then save the dashboard. See [Create and edit a dashboard](/user-guides/dashboards/create-and-edit-dashboard). |
| **Reports** | Use the same CSAT blocks in the report builder, select the company and reporting period, and save. See [Reporting](/user-guides/reporting/index#native-psa-csat-in-reports). |

These CSAT views can include other connected feedback sources alongside Autotask. Check the company selection, dates and survey filter before you read a total as Autotask-only.

### If Autotask CSAT is missing

Connecting Autotask does not turn on the import by itself. Check that **Import satisfaction ratings** is saved, **Satisfaction feedback** is granted, the companies are linked, the tickets have synced and the reader has the CSAT permission. If the **Import satisfaction ratings** switch does not appear at all, contact MSPortal support.

## Additional Configuration

After completing setup, you may want to configure additional settings:

### Configure Ticket Settings

Navigate to **Settings** > **Tickets** to:

1. Set the **Delivery Method** to **PSA**
2. Ensure **Autotask** is selected as your PSA provider
3. Configure ticket categories and map them to Autotask ticket types
4. Set **Ticket Defaults** for tickets created from compliance tasks or automation

<Tip>
  Ticket defaults are also used as the starting point for new ticket templates, making template creation faster.
</Tip>

### Configure Display Groups

Display groups control which ticket fields users can see based on their role.

1. Navigate to **Settings** > **Tickets**
2. Scroll to **Display Groups** and click **Create Group**
3. Configure:
   - Name for the display group
   - Select **Autotask** as the PSA provider
   - Assign roles that should use this display group
   - Select which fields are visible

<Warning>
  Only grant access to information users need for their role. Follow the principle of least privilege.
</Warning>

### Configure Allowed Statuses

Set which ticket statuses users can select when updating tickets:

1. Navigate to **Settings** > **Tickets**
2. Configure status permissions for each display group

<Tip>
  We recommend preventing users from closing tickets directly. Instead, use a "Ready for Review" status to ensure tickets are reviewed before closure.
</Tip>

## Devices from Autotask configuration items

MSPortal treats an RMM, MDM or network tool as the source of truth for a device. When an RMM is connected, a Autotask configuration item keeps or creates a device only when its type has **Auto-import** on and is not ignored in [Import Devices](/user-guides/integrations/import-devices). Configuration items of other types add their details to devices your RMM reports.

- **Configuration items removed in Autotask.** Once a day MSPortal checks the full list of active configuration items in Autotask. A configuration item that is deleted or made inactive is removed from staging three days after Autotask stops listing it, and stays if it comes back in the meantime.
- **What happens to the device.** When the configuration item leaves staging, its device moves to another integration that still reports it, such as your RMM. A device nothing else reports is removed. In a tenant with an RMM, an IT Glue or other PSA record keeps the device only when its type has Auto-import on.

Only companies still mapped to this connection are affected. Unmapping a company or excluding a type stops syncing those records and keeps their devices. Archived devices are never removed.

## Troubleshooting

| Issue | Solution |
|-------|----------|
| Connection test fails | Verify your API username and secret are correct. Ensure the API user has the MSPortal security role. Read the reported error text. |
| A data option is unavailable | Check its result in **Permissions**, grant the named permission and select **Re-check**. |
| Tickets not syncing | Check that the correct queues and categories are selected in **Choose data** and that ticket statuses aren't excluded. The note under **Categories** lists categories that don't sync, including ones added in Autotask after setup. See [Fix missing tickets](/user-guides/integrations/faq#fix-missing-tickets). |
| Companies or tickets are missing | Check saved filters in **Choose data**, the result in **Sync activity** and company links. |
| New statuses are absent | Wait for metadata to sync, check the selected queues and reload the task. |
| Webhooks not working | Ensure your API user's security role can create webhooks, then contact MSPortal support. |
| Missing data | Verify the API user has appropriate permissions in the MSPortal security role. |
| Contacts not importing | Verify **Enable Auto-Import** is on and a default role is selected in **Choose data**. |
| Setup finished but records are absent | Check background errors in **Sync activity**, imports you have not run yet and the selected company. |
| Projects load, but a status or task edit fails | Check the API user's Projects **Edit** access, task restrictions and Line of Business scope. |
| Creating a project or applying a template fails | Check create access to Projects, Phases and Tasks, and the resource and work type choices. Check partial results before retrying. |
| Logging project time fails | Check **TimeEntries** create access, **Can enter time on**, the resource mapping, billing field permissions and Autotask's completed task and timesheet rules. |
| Survey results are missing from CSAT views | Check the saved **Import satisfaction ratings** switch, the security level's survey rating rights, company links, synced tickets and the reader's CSAT permission. |

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Does Test connection only test credentials?">
    Yes. Select **Save and continue** after a successful test to create a connection, or **Save changes** to save replacement credentials on an existing connection.
  </Accordion>
  <Accordion title="Does a green permissions result verify ticket writes?">
    No. The permission checks probe read access. Creating tickets, comments or other changes in Autotask needs the relevant write permission and a successful action.
  </Accordion>
  <Accordion title="Does Finish setup mean all data is ready?">
    No. Check the background sync result and verify company, user and device imports separately.
  </Accordion>
  <Accordion title="Will every discovered contact receive portal access?">
    Discovery and import are separate. Review user matches, company links and the permissions assigned to portal users; invitation is a separate workflow.
  </Accordion>
  <Accordion title="Can I dashboard or report on Autotask native survey results?">
    Yes. Turn on **Import satisfaction ratings** in the Autotask connection's **Choose data** task and grant the API user's security level the survey rating rights. Completed survey results are available in the CSAT Dashboard, custom dashboard CSAT widgets, report blocks and CSV exports, subject to company mapping and role access. You can keep using Autotask's own surveys; Simplesat is not required.
  </Accordion>
  <Accordion title="Can I replace saved credentials by retesting the form?">
    A retest only verifies access. Select **Save changes** after testing the replacement credentials, then confirm the saved connection before revoking the old credential.
  </Accordion>
</AccordionGroup>
