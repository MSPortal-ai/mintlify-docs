Use this **MSP staff** workflow to connect Autotask PSA and configure the data available to your portal. The wizard follows **Connect → Permissions → Sync → Configure → Import**. Company users do not administer this connection.

MSPortal supports syncing **Autotask native survey results** and presenting them in the **CSAT Dashboard**, custom dashboard widgets, report blocks and CSV exports. Enable **Import satisfaction ratings** in the Autotask connection's **Sync** step; it is off by default. You can continue collecting feedback through Autotask's own surveys.

## Before you start

You need integration-management permission, authorized provider credentials and access to the companies you intend to synchronize. Ticket configuration can additionally require Ticket Settings permission. Keep credentials in the connection form and your approved secret store.

Create a dedicated Autotask API-only user and an appropriate API-user security level. Generate its key/secret and configure the integration’s vendor tracking identifier in Autotask. The wizard asks for the API username and secret; it does not expose a field for a custom tracking ID. If tracking is rejected, confirm the correct vendor association with your administrator. See [API-user setup](https://autotask.net/help/developerhelp/content/apis/General/Define_API_User.htm) and [REST authentication](https://www.autotask.net/help/DeveloperHelp/Content/APIs/REST/General_Topics/REST_Security_Auth.htm).

## Connect the provider

1. Open **Settings > Integrations**, find **Autotask PSA**, and open setup. Use **Configure** for the existing connection.
2. Enter **API Username** and **API Secret**.
3. Select **Test Connection** when ready to connect. **For a new connection, a successful test also creates and saves the integration.** There is no separate Create Integration button in this PSA wizard.
4. Review the result and continue to **Permissions**. An existing connection can initialize with a Connected indicator; that is not proof of a fresh test.

## Check permissions

The permission screen checks vendor endpoints and reports required access, optional access and unavailable or unverified results. Required denied access prevents the supported progression. An optional permission that is not granted keeps its corresponding sync off.

Read the reported failure before changing the API role. A timeout, unavailable endpoint or unverified check is not automatically proof of a missing permission. Retry after resolving the actual problem. These checks exercise **read access**; they do not prove that ticket creation, comments, warranty updates or other writes will succeed.

## Project management permissions

Edit the security level assigned to the **API-only user whose credentials are saved in MSPortal** under **Admin > Resources/Users > Security Levels**. Configure access to the **Projects** module and its create/update operations, as well as the supporting records below. A human technician’s security level does not replace the API user’s access.

Autotask distinguishes **project tasks** from service tickets. Service Desk ticket edit permission alone is not sufficient. The table describes the effective access the API user needs; custom security levels can express this through module settings and additional options rather than a separate checkbox for each API entity.

| Project operation | Required effective API-user access |
| --- | --- |
| Read the portfolio and project details | **Projects → Project: View (All)**, including the intended companies and Lines of Business. |
| Create projects, including from MSPortal templates | Project **Add** access. |
| Update project status, dates and mapped project fields | Project **Edit** access across the intended projects. |
| Read, create and update phases | Query, create and update access to **Phases** through the Projects module. |
| Read, create and update project tasks | Query, create and update access to **Tasks**, including status, primary resource, priority, title, estimated hours, dates and mapped task fields. Do not restrict the API user to tasks assigned to itself. |
| Read project effort and time-entry notes | Query access to **TimeEntries** for the intended project tasks and resources. |
| Log time against project tasks | Create access to **TimeEntries**; configure the Projects **Can enter time on** setting for the intended tasks and permission to enter time for the selected resource. Enable the applicable billing-field permissions when setting billable/non-billable time. |
| Populate company, contact and assignment choices | Read access to **Companies**, **Contacts**, **Resources**, **Roles**, **Departments** and the work types/billing codes used by your tasks and time entries. |
| Populate statuses, priorities, types and mapped fields | Read access to the relevant project/task picklists and user-defined-field definitions. |

Use unrestricted project access within the intended organizational scope for the integration. Autotask can restrict task visibility by **Line of Business even with View All**. Baseline project tasks are read-only, and time-entry rules for completed tasks, project types and submitted/posted time still apply. See Autotask’s [task access rules](https://www.autotask.net/help/Developerhelp/Content/APIs/REST/Entities/TasksEntity.htm) and [time-entry requirements](https://ww2.autotask.net/help/developerhelp/Content/APIs/REST/Entities/TimeEntriesEntity.htm).

### Notes, checklists and templates

In MSPortal, Autotask project-task notes use **time-entry notes**; standalone project-task note creation and editable checklist items are not supported in this workflow. Additional note or checklist permissions will not enable an unsupported control. Creating or applying a saved MSPortal template to an Autotask project requires the project, phase and task create permissions above.

MSPortal-only projects, reusable portal templates and portal project registers use MSPortal permissions. Vendor permissions apply when an action explicitly creates or updates PSA work. These project read/create/update operations do not require blanket Delete access or an administrator account.

### Verify read and write access separately

After saving the API user’s security level, return to **Settings > Integrations > Autotask PSA > Configure > Permissions** and select **Re-check**. A green Projects result checks project reading; it does not verify phase/task creation, edits or time entry.

An Autotask administrator can also inspect the API user’s effective query/create/update access using Autotask’s [entityInformation permissions](https://www.autotask.net/help/Developerhelp/Content/APIs/REST/API_Calls/REST_EntityInformationCall.htm). Validate the intended project creation, task edit and time-entry workflows on a designated test project. If a template operation partly succeeds, inspect the created records before retrying.

## Select synchronization scope

Select the intended queues and ticket categories. Decide whether to include recurring tickets. Review company/contact filters and the supported opportunity, project, invoice, product catalog, configuration-item, change-management and satisfaction-rating options. Configuration items first synchronize into device staging; discovery is not a completed device import.

Review filters before continuing. Synchronizing source records, linking them to companies and importing portal records are separate steps. Automatic company/contact import options can create portal records when matching source records arrive. Review any import preview and the selected categories carefully; do not rely on a confirmation appearing for every save.

Proceeding from Sync saves the selected scope and starts background synchronization. Options in later steps may remain incomplete while it runs. Check errors and the connection’s actual sync result before treating an empty list as the final dataset.

Warranty writeback is an optional **vendor write**. Enable it only when you intend resolved warranty data to update the connected PSA records.

## Write warranty dates back to Autotask

Warranty writeback copies each device's warranty expiration date from MSPortal into the **Warranty Expiration Date** of its Autotask configuration item. It does not need **Enable configuration item sync**, so it also works when your configuration items are created by Datto RMM rather than imported into MSPortal.

<Frame caption="Branch preview: Warranty writeback on the Sync step, with configuration item sync turned off.">
  <img src="/images/product/autotask-sync-warranty-writeback.png" alt="Autotask Sync step showing the Warranty writeback switch and its matching description while Enable configuration item sync is off" width="1090" height="390" />
</Frame>

MSPortal matches each device to a configuration item in this order:

1. **RMM device UID.** A device from Datto RMM matches the configuration item that carries the same RMM device UID.
2. **Serial number.** Otherwise, MSPortal looks for exactly one active configuration item with the same serial number in the Autotask company mapped to the device's company.

Devices imported by configuration item sync are already linked to their configuration item and are updated directly. A match is skipped when the serial number is missing, a placeholder such as "To be filled by O.E.M.", or shared by more than one configuration item. A configuration item that matches two MSPortal devices is also skipped, so two devices never compete for one record. MSPortal never matches by device name.

<Steps>
  <Step title="Grant edit access">
    Give the API user's security level **Inventory > Configuration Item** access of **View (All)** and **Edit**, then use **Re-check** under **Permissions**.
  </Step>
  <Step title="Turn it on">
    Open **Settings > Integrations > Autotask PSA > Configure > Sync** and turn on **Warranty writeback**. Continue from Sync, or use **Save & Exit**, to save the setting.
  </Step>
  <Step title="Verify a device">
    Writeback runs daily. The first run covers every device with a successful warranty check; later runs send only devices whose warranty was checked again. Open a known device's configuration item in Autotask and confirm **Warranty Expiration Date**.
  </Step>
</Steps>

Only devices with a successful warranty check and a known expiration date are written. A configuration item that already shows the same date is left unchanged. If your Autotask configuration items sync one way into IT Glue, that sync carries the date into the IT Glue configuration as well. To write IT Glue configurations directly, see [Warranty writeback to Hudu and IT Glue](/user-guides/integrations/documentation-warranty-writeback).

## Import Autotask native CSAT for dashboards and reports

This imports survey results already collected by Autotask's built-in surveys. You do not need Simplesat or a new MSPortal survey to present those responses.

1. Open **Settings > Integrations > Autotask PSA > Configure**.
2. Give the API user's security level the survey rating rights. In Autotask, open **Admin > Resources/Users > Security Levels**, edit the level assigned to the API user, and under **Other > Surveys** enable **Can view Organization Survey Ratings and Contact Survey Ratings** and **Can view Resource Survey Ratings**. In **Permissions**, check the **Satisfaction feedback** result and use **Re-check** after resolving denied access.
3. Open **Sync** and enable **Import satisfaction ratings**. There is no rating scale to choose: Autotask survey questions rate **1 to 5**, and each completed survey's overall rating is rounded to a whole rating on that scale.
4. Continue from Sync to save the selection, or use **Save & Exit**. Saving starts the first import; later imports run hourly. Saving is not proof that all responses have arrived.
5. Ensure the results' companies are linked to portal companies and their tickets have synchronized. A result whose company is not linked will not appear in company-scoped CSAT results until a later sync can resolve it. Technician attribution uses the assigned resource on the synchronized ticket.
6. Grant intended readers **Surveys > Read > CSAT** in their role. Dashboard and report authoring also require the corresponding permissions.

Only completed surveys are imported. Surveys that were sent but not answered, and surveys completed without answering any rated question, are not counted as responses. Autotask's REST API does not expose free-text survey answers, so imported responses carry ratings only.

### Present the imported results

- **CSAT Dashboard:** open **Surveys > CSAT Dashboard** to read scores and trends, or export responses. Imported Autotask results are grouped under **Autotask PSA satisfaction**. See [Read and export support satisfaction feedback](/user-guides/surveys/read-csat-feedback).
- **Custom dashboards:** add **CSAT Overview**, **CSAT Trend**, **CSAT by Company**, or **Recent CSAT Feedback** from the widget library, then save the dashboard. See [Create and edit a dashboard](/user-guides/dashboards/create-and-edit-dashboard).
- **Reports:** use the same CSAT blocks in the report builder, select the intended company and reporting period, and save. See [Reporting](/user-guides/reporting/index#native-psa-csat-in-reports).

These CSAT views can include other connected feedback sources alongside Autotask. Check company selection, dates and any available survey filter before interpreting a total as Autotask-only.

### If Autotask CSAT is missing

An empty dashboard or missing widget does not mean Autotask native CSAT is unsupported. Check the saved import toggle, the survey rating permissions, integration status and last import result, company links, synchronized tickets, selected dates and the reader's CSAT permission. Merely connecting Autotask does not turn on satisfaction imports. If the **Import satisfaction ratings** control itself is absent, contact MSPortal support to check the connection and feature availability.

## Configure portal behavior

Configure closed statuses, client-comment status and resolution status groups for the chosen ticket scope. Review opportunity stages/probabilities/types and invoice settings when enabled. Missing queue/category choices may mean the first metadata sync is incomplete.

Configuration forms save changes automatically after editing. Wait for the saved state; wizard navigation waits for pending saves and reports failures. Leaving the screen is not a substitute for checking a failed save. Ticket defaults additionally require Ticket Settings permission.

**Quick Sync** requests ticket synchronization. **Clear & Resync** clears portal ticket data for this connection before reloading it. Use the latter only for an intended rebuild, and check the subsequent result; it is not a harmless refresh.

## Import and finish

The Import step offers **Users**, **Companies** and **Configuration Items**. **Open Configuration Item Import** opens the separate staging/import page. Review existing portal records before creating duplicates. Company links determine which client can see synchronized data.

Apply the intended company and user selections and check the result. **Complete Setup** also attempts to apply pending company/user imports before completing the wizard. It can start background work, so setup completion is not proof that every import or sync succeeded. An import-page link only navigates to that workflow.

Use **Save & Exit** to save wizard progress when pausing. Reopen the connection to continue and verify the saved state. Portal invitations and client permissions remain separate from discovering provider contacts.

## Maintain the connection

Reopen setup to inspect scope and errors. A successful retest of changed fields is not proof of credential rotation: this wizard has no separate update-credentials action. Confirm the supported replacement path before revoking working vendor credentials.

**Delete Integration** opens a named confirmation. Confirm **Delete** only to remove the connection and its associated settings; cancel preserves it. Vendor-side credential revocation is separate.

## Troubleshooting

| Symptom | What to check |
| --- | --- |
| Projects load, but a status or task edit fails | Review the API-only user’s Projects Edit access, task restrictions and Line of Business scope. |
| Creating a project or applying a template fails | Check create access to Projects, Phases and Tasks, and the required resource/work-type choices. Inspect partial results before retrying. |
| Logging project time fails | Check TimeEntries create access, **Can enter time on**, resource mapping, billing-field permissions and completed-task/timesheet rules. |
| Connection fails | Correct provider fields, credential validity, account/API endpoint and error text. |
| A data option is unavailable | Permission result and whether this provider supports that option. |
| Companies or tickets are missing | Saved provider filters, synchronization result and company links. |
| New statuses are absent | Metadata synchronization, selected board/team/queue scope and latest load. |
| Setup finished but records are absent | Pending imports, background errors and the correct company context. |
| Survey results are missing from CSAT views | Saved **Import satisfaction ratings** toggle, the security level's survey rating rights, company links, synchronized tickets and the reader's CSAT permission. |

## Frequently asked questions

<AccordionGroup>
  <Accordion title="Does Test Connection only test credentials?">
    For a new connection, a successful test also creates the integration. Enter credentials only when you intend to connect it.
  </Accordion>
  <Accordion title="Does a green permissions result verify ticket writes?">
    No. The permission checks probe read access. Creating tickets, comments or other vendor changes needs the relevant write permission and a successful action.
  </Accordion>
  <Accordion title="Does Complete Setup mean all data is ready?">
    No. Check the background sync result and verify company, user and device imports separately.
  </Accordion>
  <Accordion title="Will every discovered contact receive portal access?">
    Discovery and import are separate. Review user matches, company links and the permissions assigned to portal users; invitation is a separate workflow.
  </Accordion>
  <Accordion title="Can I dashboard or report on Autotask native survey results?">
    Yes. Enable Import satisfaction ratings in the Autotask integration's Sync step and grant the API user's security level the survey rating rights. Completed survey results are available in the CSAT Dashboard, custom dashboard CSAT widgets, report blocks and CSV exports, subject to company mapping and role access. You can keep using Autotask's own surveys; Simplesat is not required.
  </Accordion>
  <Accordion title="Can I replace saved credentials by retesting the form?">
    Do not treat a successful retest as proof that replacement credentials were saved. This wizard does not provide a separate credential-update action; confirm the supported update path before revoking the old credential.
  </Accordion>
</AccordionGroup>
